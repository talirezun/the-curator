# The Curator — Development Guide

This file exists so any new Claude session can immediately understand the project state, architecture, known issues, and active design decisions without re-reading git history or debugging from scratch.

---

## What This Project Is

The Curator is a local Node.js web application that ingests text sources (PDF, MD, TXT) and automatically builds an interconnected knowledge wiki. The wiki is stored as plain markdown files, readable by Obsidian as a visual knowledge graph.

**Core loop:**
1. User drops in a source → LLM reads it → writes wiki pages (entities, concepts, summary)
2. Each subsequent ingest updates existing pages instead of duplicating them
3. Obsidian reads the same files → renders a graph where nodes are entities/concepts, edges are `[[wikilinks]]`

**Philosophy:** Compiled knowledge (persistent wiki), not retrieval (RAG). The wiki compounds with every ingest.

## Working state

This repository's working state lives in The Curator (project `projects/curator`, see
`.curator-project`). At the START of every session call the my-curator MCP tool
`get_working_state` with project "curator" and scope "latest" and read the standing
brief before acting. SAVE with `save_working_state` under project "curator", in ONE scope per
session named `session-YYYY-MM-DD-topic` (the standing brief's rule; `scope: "latest"` opens the
newest), after every material decision and at least every ten tool calls, and ALWAYS
before you stop; a save overwrites, so send the complete state each time.

## Key Functions (files.js)

| Function | Purpose |
|---|---|
| `writePage(domain, relativePath, content)` | Normalise path → dedup passes A+B → cross-folder dedup (3b) → inject frontmatter → capture pre-write state → merge with existing → strip blanks → dedup bullets → strip folder-prefix links → normalize variant links (5c: entities + concepts + summaries, prefix-tolerant) → write → call injectSummaryBacklinks if summary → return `{canonPath, status, bytesBefore, bytesAfter, sectionsChanged, bulletsAdded}` (v2.5.0+; null on invalid input) |
| `compileConversation(domain, conversationId, onProgress, opts)` | Conversation compile: load conversation → refuse if fewer than `MIN_USER_MESSAGES` user turns (**1** since v3.0.1-beta.15, was 2) → compute deterministic summary slug `<title>-YYYY-MM-DD-<4hex>` → refuse if file already exists at slug (idempotency guard) → **3-step LLM ladder `full → concise → summary-only`** (v3.0.1-beta.27), escalating ONLY on `isOutputTokenLimit(err)` or a JSON parse failure; any other LLM error (503/429/auth/network) surfaces immediately → write all pages via the same writePage pipeline → syncSummaryEntities → programmatic mergeIntoIndex (no LLM-driven index regen) → appendLog → return `{ok, title, pagesWritten, changes, warnings}`. `opts.generateText` is a **test-only** seam (defaults to the real one) for driving the ladder offline. |
| `syncSummaryEntities(domain, summaryPath, writtenPaths)` | Post-ingest reconciliation: injects ALL written entity AND concept slugs into summary's "Entities Mentioned", then re-fires injectSummaryBacklinks with the complete list |
| `injectSummaryBacklinks(summarySlug, content, wikiDir)` | For each entity in "Entities Mentioned", injects `[[summaries/slug]]` into that entity's Related section; checks entities/ first, falls back to concepts/; creates the section if it doesn't exist |
| `deduplicateBulletSections(content)` | Safety net: removes duplicate bullets from all ACCUMULATE sections using dedupKey; runs after every write and after syncSummaryEntities |
| `mergeWikiPage(existing, incoming)` | Union merge: incoming is base, bullets from existing ACCUMULATE sections are injected (Key Facts, Related, Entities Mentioned, etc.). **Prose preservation (v3.0.1-beta.15):** any `## ` PROSE section present in `existing` but ENTIRELY ABSENT from `incoming` is preserved (case-insensitive match), so a thin Compile/Curate edit can't wipe an existing page's Definition / Summary / Why It Matters. If `incoming` includes the heading, incoming wins (no duplication). Exported for unit testing. |
| `injectBulletsIntoSection(content, sectionName, bullets)` | Dedup-aware bullet injection: compares by link target; creates the section if it doesn't exist (uses 'im' multiline regex for existence check) |
| `stripBlanksInBulletSections(content)` | Removes blank lines inside bullet sections (LLM artifact) |
| `normalizePath(relativePath)` | Redirects non-canonical folders → entities/ or concepts/ |
| `injectFrontmatter(content, path, today)` | Extracts inline Tags/Type/Source → builds YAML frontmatter block |

## Ingest Pipeline Flow

```
POST /api/ingest
  → ingestFile(domain, filePath, originalName)
      1. Save to raw/
      2. Extract text (pdf-parse or readFile), cap at 80k chars
      3. Load domain CLAUDE.md schema + current index.md
      4. Read existing entity/concept filenames → pass to LLM prompt
         (prevents LLM creating lumina.md when lumina-ai.md exists)
      5. Single-pass LLM call (< 15k chars input)
         OR multi-phase for large docs:
           Phase 1: outline → [{path, summary}]
           Phase 2: batched content (BATCH_SIZE=4 pages/call)
           Phase 3: index update
      5.5 Deduplicate result.pages — multi-phase can return the same path in
           multiple batches; keep last occurrence per path (Map dedup)
      6. writePage() for each page:
           a. normalizePath() — canonical folder enforcement
           a2. Underscore → hyphen slug normalisation — two_worlds_of_code.md → two-worlds-of-code.md
           b. Pass A: title-prefix strip — dr-tali-rezun.md → tali-rezun.md
           c. Pass B: hyphen-normalised dedup — talirezun.md → tali-rezun.md
           c2. Step 3b: cross-folder dedup — concepts/google.md → entities/google.md
               (prevents duplicate files when LLM misclassifies entity as concept)
           d. injectFrontmatter()
           e. mergeWikiPage() if file exists
           f. stripBlanksInBulletSections()
           g. deduplicateBulletSections() — safety net for merge edge cases
           h. Strip [[entities/...]] and [[concepts/...]] folder-prefix links
           i. Step 5c: normalize [[variant]] links using Pass A+B+C logic
              Pass A: [[dr-tali-rezun]] → [[tali-rezun]]
              Pass B: hyphen-normalised match against entities + concepts
              Pass C: prefix-tolerant match across all wiki files (entities, concepts, summaries)
              Catches [[energy-and-water-footprint-of-generative-ai]] →
              [[summaries/the-energy-and-water-footprint-of-generative-ai]]
           j. writeFile()
           k. If summary page: injectSummaryBacklinks() (entities/ + concepts/ fallback)
           l. Return canonPath — the actual path written to disk (may differ from input)
      7. syncSummaryEntities() ← THE KEY POST-WRITE STEP
           Uses canonicalPaths (returned by writePage), NOT original LLM paths.
           This ensures redirected slugs (dr-tali-rezun → tali-rezun) appear
           correctly in the summary. Injects ALL entity AND concept slugs into
           summary's "Entities Mentioned" → deduplicates → re-fires
           injectSummaryBacklinks() with the complete list →
           ALL entities/concepts get bidirectional backlinks
      8. writePage(index.md)
      9. appendLog()
```

## Known LLM Compliance Failures (and how they're handled)

The LLM produces structurally valid but consistently incomplete output. These patterns recur across every ingest regardless of model:

| Failure | Frequency | Code fix |
|---|---|---|
| "Entities Mentioned" lists 5–7 entities while 20–30 entity pages are written | Every ingest | `syncSummaryEntities()` in post-write step |
| Entity slug hyphen variation: `talirezun` vs `tali-rezun` | Common | Pass B dedup in `writePage()` (filename) + Pass B in `injectSummaryBacklinks()` |
| Title prefix ghost files: `dr-tali-rezun.md` | Occasional | Pass A strip + redirect in `writePage()` |
| `[[dr-tali-rezun]]` written as a link in page content | Occasional | Step 5c in `writePage()` normalizes all variant links at write time |
| Folder-prefix links: `[[concepts/rag]]` instead of `[[rag]]` | Common | `writePage()` step h strips `entities/` and `concepts/` prefixes |
| Multi-phase returns same page path in multiple batches | Occasional | `result.pages` deduped in `ingest.js` before the write loop |
| Duplicate bullets in sections (from multi-write edge cases) | Occasional | `deduplicateBulletSections()` safety net on every write |
| Entity has no Related section — backlinks silently dropped | New entities | `injectBulletsIntoSection()` now creates the section if it doesn't exist |
| Summary truncated — missing "Entities Mentioned" section entirely | Occasional (large docs) | `syncSummaryEntities()` adds the section if missing |
| Blank lines between bullets in a section | Common | `stripBlanksInBulletSections()` runs on every write |
| Underscore filename from PDF name: `two_worlds_of_code.md` | Occasional | Step 1a in `writePage()` converts `_` → `-` in the filename |
| Cross-folder duplicates: `concepts/google.md` when `entities/google.md` exists | Common | Step 3b cross-folder dedup redirects to existing file |
| Slug mismatch: `[[international-energy-agency]]` but file is `iea.md` | Occasional | Prompt strengthened + Step 5c Pass C prefix-tolerant matching |
| Missing article prefix in link: `[[energy-and-water...]]` vs `the-energy-and-water...` | Occasional | Step 5c Pass C strips `the-`/`a-`/`an-` prefixes for matching |
| Semantic near-duplicates in Key Facts ("25 years" vs "30 years") | Common | NOT fixed — requires LLM or manual curation |
| Concepts filed as entities (llm.md, cli.md, open-source.md) | Occasional | Caught by manual review; no automated fix |

## Post-Ingest Quality Checklist

Run these after any ingest where results look wrong:

```bash
# 1. Ghost author links (LLM uses "talirezun" or "dr-tali-rezun")
grep -rl "\[\[talirezun\]\]\|\[\[dr-tali-rezun\]\]" domains/articles/wiki/

# 2. Folder-prefix link violations
grep -rl "\[\[concepts/\|\[\[entities/" domains/articles/wiki/ | grep -v index.md

# 3. Duplicate bullets in any section
python3 -c "
import os, re
wiki = 'domains/articles/wiki'
for root, dirs, fnames in os.walk(wiki):
    for f in fnames:
        if not f.endswith('.md'): continue
        path = os.path.join(root, f)
        c = open(path).read()
        if len(re.findall(r'^## Related\s*$', c, re.M)) > 1:
            print('DUPLICATE RELATED:', path)
"

# 4. Duplicate Related sections (created by buggy section injection)
grep -rl "^## Related" domains/articles/wiki/ | xargs python3 -c "
import sys, re
for p in sys.argv[1:]:
    c = open(p).read()
    if len(re.findall(r'^## Related\s*\$', c, re.M)) > 1: print(p)
" 2>/dev/null

# 5. Run retroactive backlink repair if needed
node scripts/inject-summary-backlinks.js --domain=articles
# or all domains:
node scripts/inject-summary-backlinks.js
```

**Fix ghost links globally:**
```bash
# NOTE: every substitution needs its own -e. The first script cannot be bare
# when a second -e follows — BSD sed then reads "-e" as a FILENAME and exits 1
# having changed nothing (silent no-op; verified).
find domains/articles/wiki -name "*.md" -print0 | xargs -0 sed -i '' \
  -e 's/\[\[talirezun\]\]/[[tali-rezun]]/g' \
  -e 's/\[\[dr-tali-rezun\]\]/[[tali-rezun]]/g'
```

## Wiki File Conventions

**Three canonical folders only** — the code enforces this:
- `entities/` — specific people, tools, companies, frameworks, datasets
- `concepts/` — ideas, techniques, methodologies, principles
- `summaries/` — one page per ingested source document

**Link syntax** — always `[[page-name]]` without folder prefix, EXCEPT summaries which use `[[summaries/slug]]` because they live in a subfolder Obsidian needs for routing.

**YAML frontmatter** — every page gets it injected automatically by `injectFrontmatter()`. The LLM is instructed NOT to produce frontmatter. Type tags drive Obsidian graph coloring:
- `type/entity` → Blue nodes
- `type/concept` → Green nodes
- `type/summary` → Purple nodes

**Merge strategy** — bullet-accumulating sections (Key Facts, Related, Entities Mentioned, etc.) grow with every ingest. Prose sections (Summary, Definition) use the incoming LLM version (it had full document context).

In Graph View → ⚙ → Groups:
| Group | Query | Color |
|---|---|---|
| Entities | `tag:#type/entity` | Blue |
| Concepts | `tag:#type/concept` | Green |
| Summaries | `tag:#type/summary` | Purple |

The vault root should point to `domains/<domain>/wiki/` (or a parent folder covering multiple domains). Use the Knowledge Base Location shown in the Domains tab.

**To check connections for a specific entity** (e.g. the author):
- Filter graph for the entity name
- Enable Orphans toggle to show unconnected nodes
- Every summary the author wrote should show as a purple node connected to the entity

```

  geminiApiKey          — Google Gemini key (set via Settings tab / onboarding wizard)
  anthropicApiKey       — Anthropic Claude key (set via Settings tab)
  domainsPath           — custom path for domains/ folder (set via UI)

.env                    — developer fallback for API keys (never committed)
  GEMINI_API_KEY        — Google Gemini (default, recommended)
  ANTHROPIC_API_KEY     — Anthropic Claude (alternative)
  LLM_MODEL            — optional model override
  DOMAINS_PATH         — optional custom path for domains/ folder

.sync-config.json       — GitHub sync credentials (never committed)
```

**Key priority:** `.curator-config.json` (Settings UI) takes precedence over `.env` for API keys.
**LLM selection:** dispatch is still on `getActiveProvider()`, but **last-saved-wins is retired** (v3.45.0, "Option B"). Saving a key sets the active provider **only when nothing is active yet** — i.e. on the first key of a fresh install; after that the key is saved and the build lane does not move, and the save reports the deferral rather than performing it. **Choosing the build model is the writer from then on**: `POST /api-keys/build-model` sets both the model and, with it, the provider — one gesture, at the surface whose whole subject is what builds your wiki. **Disconnecting the ACTIVE provider falls to the cheapest measured connected provider** (`clearApiKey` takes a `rank` and a `canActivate`, verifies the ranked proposal is the same SET before trusting it, and records `null` — the decision — when every candidate is refused, because an ABSENT field is what the legacy ladder re-infers from). Set **`ACTIVE_PROVIDER_DERIVED = false`** in [src/brain/config.js](src/brain/config.js) to restore last-saved-wins wholesale. `getProviderInfo()` in `llm.js` honours the resolved provider, falling back to whichever provider still has a usable key if the active one's key is missing. Gemini-first-if-both applies only to **legacy configs with no `activeProvider` field**. The cost is stated rather than hidden: a user pasting a key in order to SWITCH now needs one more click — taken knowingly, because the silent version moved the build lane and the bill without asking.
**Default models:** pinned in `DEFAULTS` in [src/brain/llm.js](src/brain/llm.js) — currently `gemini-2.5-flash-lite` / `claude-haiku-4-5` (Haiku is the low-cost tier chosen to match Flash Lite's cost profile; opt into Sonnet with `LLM_MODEL` in `.env`).

## Active Development Decisions

- **No vector DB / embeddings** — the decision stands, but **not** because the wiki fits in one context window; it stopped fitting long ago (the real `articles` wiki is ~4.4 MB against a 60 KB content budget). What replaced the "just send everything" assumption is **query-driven retrieval in `src/brain/chat.js`**: entity-pivot detection, keyword scoring, and a compact slug catalogue select the pages to load within `CONTENT_BUDGET_CHARS` (60 KB), `CATALOGUE_BUDGET_CHARS` (12 KB) and `MAX_PAGES_LOADED` (50). The reason to stay embedding-free is that the `[[wikilink]]` graph is already a hand-curated relevance signal, and markdown files stay human-readable and Obsidian-native — not that the corpus is small. (A blunt 90 KB `slice()` was the pre-beta.11 behaviour and was a genuine bug: on a mature domain the chat saw only `index.md` and `log.md`.)
- **No React/Vue** — a three-place rail, Chat · Domains · Context, with Sync and Settings in the footer (v3.64.0; was a seven-tab UI Chat · Ingest · Wiki · Health · Domains · Sync · Settings). Ingest and Shared Brain moved onto the domain page as HOSTED_VIEWS — hosted sections, registered and navigable, but with no rail button of their own — and, since v3.64.1, are laid out as five numbered sections under an OVERVIEW card, with their open/closed fold state and the PAGES lens held as one install-wide preference rather than per domain. **Six standing design rules, from v3.64.2 (the fourth added v3.65.0, the fifth and sixth v3.65.1), for every view builder from now on:** (1) **one overview card** (`renderOverview()` in `shared/overview.js`) for the readings *about* a screen, shared by every host rather than each view growing its own — the domain page's OVERVIEW and the Context page's three-layer readings are the same component, one rendered function, not two; (2) **one heading rule** — every numbered section on a page carries a numeral at one fixed x position and a Title-case title (e.g. 1 Ingest, 2 Pages, 3 Projects in this domain, 4 Shared Brain, 5 Wiki health, not ALL CAPS) above its own card, the head a SIBLING of the card or fold and never a wrapper around it; (3) **the step-body rule** — a step or section's body is uniform fold rows, with the explanation only in the ⓘ, never inline, and its one standing exception since v3.16.1: a warning, a cost or an outcome may never sit behind a chevron; (4) **the monitor** (`renderMonitor()` in `shared/monitor.js`, v3.65.0) — every LIVE-STATE reading in the app renders through one recessed, mono-faced component, distinguished from a `.cur-group` and from a fold row's `<summary>` (an incidental reading), with the v3.16.1 exception carried INSIDE it as a `loud` entry — always rendered, never wrapped in a `<details>`; (5) **continuity by identity** (v3.65.1) — one domain, one colour, EVERYWHERE it is named: one palette (the twelve `.cur-sb-dot-N` rules, `shared/sidebar.css`), one mapping (`identityDotClass(i)` in `shared/sidebar.js`, keyed on the install's own domain index — position N is position N on every screen), one glyph (`.cur-sb-dot`, 8px, round, resized or reshaped by no view); a sidebar row, a Chat domain chip, an Ingest destination row, a Knowledge row and the Context breadcrumb all carry it, and no surface may invent a second mapping or a second palette; (6) **the depth bar** (`renderDepthCell()` in `shared/monitor.js`, v3.65.1) — the THIRD visual channel, SIZE/SHARE, beside TIME (the freshness dot) and WHICH DOMAIN (the identity dot, rule 5): a tinted bar behind a figure, right-anchored, its length a NAMED denominator (a budget, or the largest visible row) — never a time, never inside a `<summary>` or a sidebar row, and wherever it turns danger-toned the same fact is also stated in words, unfolded (v3.16.1). **Every sidebar in the app is also one component since v3.65.0** (`shared/sidebar.js`, `renderSidebarHead`/`Group`/`Row`) — Domains, Context and Settings all render through it: a title with no ⓘ, at most two actions stacked under it, an eyebrow group, rows of identity dot · name · figure · freshness mark · clock glyph + age · last-event line; active is the filled row (a `--mat-row-*` alpha overlay), never a left edge — the violet `::before` selection bar Settings and Chat's conversation list each once used on their own is gone from both, with no rule left to bring it back. Still vanilla JS, no build step.
- **JSON mode for ingest, text mode for chat** — ingest requires structured output; chat needs free prose.
- **Conversations gitignored from app repo but synced via knowledge repo** — personal to each user's machine, not committed to source control.
- **CLAUDE.md per domain** — each domain is a specialist, not a generalist. The schema shapes how the LLM categorises knowledge for that domain.
- **syncSummaryEntities is idempotent** — safe to run multiple times; injectBulletsIntoSection deduplicates by link target.
- **deduplicateBulletSections is always safe to run** — only removes bullets whose dedupKey already appeared earlier in the same section; never drops unique content.
- **API keys UI-first** — `.curator-config.json` (set via Settings tab / onboarding wizard) takes priority over `.env`. The `.env` file remains as a developer fallback.
- **install.sh auto-provisions** — detects and installs Node.js (via Homebrew or nodejs.org .pkg) and git (via Xcode CLI tools); no longer asks for API key during install (onboarding wizard handles it); auto-opens the app on completion.
- **No Stop button** — removed entirely because AppleScript's `on reopen` handler is broken on modern macOS and caused unrecoverable crashes. Closing the browser tab leaves the server running in the background (uses ~0 CPU). Clicking the Dock icon re-opens the browser if the server is running, or starts the server if it is not. To fully quit: right-click the Dock icon → Quit.
- **No /api/shutdown endpoint** — the server runs until the process is explicitly killed (Dock → Quit, or terminal Ctrl+C). No heartbeat or auto-shutdown.
- **Auto-update via Settings** — compares local `package.json` version with GitHub's `main` branch; runs `git fetch origin main` + `git reset --hard origin/main` + `npm install` + `bash scripts/build-app.sh` (rebuilds the .app); returns `{from, to}` short SHAs; frontend then calls `/api/restart` which spawns a new process and exits the old one. Browser auto-reloads. The hard-reset (instead of `git pull`) means the app directory is always forced to match `main` exactly — `package-lock.json` regenerated by local `npm install` runs no longer blocks the update.
- **Server auto-opens browser** — `exec('open http://localhost:3333')` runs on startup, unless `CURATOR_NO_OPEN=1` is set (used by the restart endpoint to prevent double browser tabs — the frontend reloads itself via polling).
- **Absolute node path in AppleScript** — `build-app.sh` and `install.sh` resolve the full path to `node` (via `which node`) at build time and embed it as `property nodeBin` in the AppleScript. This avoids the "node: No such file or directory" failure caused by AppleScript's `do shell script` running in a bare `/bin/sh` environment without the user's PATH. A `export PATH=...` with common node locations (`/usr/local/bin`, `/opt/homebrew/bin`) is also added as a fallback. If the user upgrades or moves Node.js, `bash scripts/build-app.sh` re-resolves the path.
- **Restart uses `process.execPath`** — the `/api/restart` endpoint uses the absolute path to the currently running Node binary (`process.execPath`) instead of bare `node`, ensuring the restarted server finds the same Node regardless of shell environment.
- **UI auto-refreshes after mutations** — after ingest, domain stats (page count, conversation count) update automatically; after sync down/both, domain dropdowns and stats also refresh; switching to the Domains or Wiki tab reloads their data. No manual browser reload needed.
- **First-run guidance is a non-blocking, dismissible panel, not a wizard (R7; two doors since v3.61.0)** — the old `/old` shell's **4**-step blocking modal (API keys → create domain → sync setup → connect Claude Desktop, with no Skip on step 1 and no Escape/backdrop-close/X) described in this bullet through v3.60.0 no longer exists: `src/public/app.js` and the rest of the old shell were deleted whole in v3.41.0, and `/` has served `/next` exclusively since. The **current** panel is [`src/public/next/views/onboarding.js`](src/public/next/views/onboarding.js), built against a private design handoff's binding decision R7 (its header comment quotes the rejection of a first-run wizard verbatim): no scrim, no `role="dialog"`, no `aria-modal`, no focus trap — a labelled region layered over the real UI, opened once from `app.js`'s `boot()`, survives `navigate()`, and every step **points** at the real surface that owns that job rather than embedding an input or posting anything itself. **Two doors, as of v3.61.0** (`DOORS` / `STEP_SETS` in `onboarding.js`), because the three-step order was actively wrong for half the app's audience: *"Build a second brain"* (id `knowledge`, lands on Domains) walks `api-key → domain → ingest` — reading a lot and wanting a wiki out of it, where nothing works without a model first; *"Give your agents memory"* (id `agent`, lands on Agent memory) walks `domain → project → bridge → api-key`, with the key step's copy corrected to name what actually needs it (*"Needed for ingest and chat. Agent memory and the bridge work without one."*) rather than the old, now-false "nothing else works without a model" claim. Neither door is stored as a persona: `deriveDoor()` re-derives which one applies from on-disk facts every paint (a stored preference would go stale the moment the user does the other thing), and pressing a door writes only `app.js`'s **existing** `curator-next-view` last-view key — no new storage key, no separate preference. The trigger for showing the panel at all is still **CONFIG-ONLY** — `hasApiKey()` reads `hasGeminiKey || hasAnthropicKey` from `GET /api/config/api-keys`, which resolve through `getApiKeys()`'s `.curator-config.json` **only, never `.env`** (the same invariant this file has stated since v3.0.13; a `.env`-only developer still sees the panel, harmlessly, since it is dismissible) — and readiness facts for every step are read the fail-safe direction: a failed fetch answers all-false, which **shows** the panel rather than hiding it.
- **My Curator MCP (v2.3.0; read+write since v2.5.2)** — a local MCP server (`mcp/server.js`) that Claude Desktop spawns as a child process via stdio. Reads markdown directly from `getDomainsDir()`; does NOT require the Curator web server to be running. The authoritative tool list is the `tools` array in [`mcp/tools/index.js`](mcp/tools/index.js) — count it there rather than trusting a number in prose. **v3.62.0 added NO tool** — `slugs` is an argument on `get_project_context` and `read_first` one on `save_foundation`, so the census below is unchanged. **v3.64.0 also added NO tool** — the release's MCP-facing work is a framing extraction (`context-framing.js`) and a stale-bridge detector surfaced through `GET /api/mcp/config` and `my-curator doctor`, not a new tool, so the census stays 24/7. **v3.65.0 likewise added NO tool** — the census stays 24/7; `get_working_state` and `get_project_context` both gained two envelope fields instead, `knowledgeDomains` and `knowledgeDomainsDefaulted`, naming which wikis a project's knowledge lives in and whether the owner chose the list or it fell back to the domain the project lives in. As of v3.59.0 it holds **24** tools: **14 read** (list_domains, get_index, get_graph_overview, get_tags, search_wiki, search_cross_domain, get_node, get_connected_nodes, get_backlinks, get_summary, get_raw_source, get_working_state, list_projects, get_project_context — which since v3.62.0 returns the foundations INDEX always, the BODIES of `readFirst` documents, and any document named in its new `slugs` argument whole, outside the 120 KB reading budget) and **10 grouped as write tools**, of which **7 actually mutate** (compile_to_wiki, fix_wiki_issue, dismiss_wiki_issue, undismiss_wiki_issue, save_working_state, save_project_brief, save_foundation) and 3 are read-only inspections that happen to sit in that block (scan_wiki_health, scan_semantic_duplicates, get_health_dismissed). **Note the two valid splits, so they are never read as a contradiction:** this file counts by SOURCE GROUPING (14 read / 10 write-block), while user-facing copy — e.g. the `/next` MCP wizard — counts by CAPABILITY (**17 that read, 7 that write**), which is the more useful framing for someone deciding what to let Claude do. Same 24 tools, same 7 mutators. **Derive the mutator list from the `refuseIfReadonly` call sites across `mcp/tools/**`, never from this prose** — that call is what makes a tool a mutator, and v3.6.1 records a wrong count in a model-read doc actively changing Claude's behaviour. The graph tools are the reason MCP exists — they expose frontmatter, tags, [[wikilink]] edges (section-labeled), and bidirectional backlinks as structured data, so a frontier model can reason about topology, not just fetch pages. The generated `claude_desktop_config.json` entry uses absolute paths (`process.execPath` + `mcp/server.js` + `--domains-path <absolute>`); moving the domains folder makes it stale — the wizard detects staleness and shows a banner.
- **MCP wizard lives in Settings** — not a top-level tab. Section uses the sync-tab three-state pattern: **landing** (hero + what/privacy grid + "Set Up My Curator" CTA), **wizard** (3 numbered steps with progress pips: Copy snippet · Paste into config · Restart & verify), **connected** (status card + Self-test / View & Edit Config cards + runtime note). The wizard also joins the onboarding overlay as step 4 ("Connect to Claude Desktop", optional, skippable). Re-entering the Settings tab always refreshes the MCP status via `refreshMcpSection()` so stale UI can't persist after closing the wizard.
- **MCP response budget is in tokens, not bytes** — 1 MB of JSON ≈ 250 k tokens, which alone saturates Claude Opus's 200 k context window. `enforceSizeLimit()` in `mcp/tools/index.js` caps at **400 KB (~100 k tokens)** so a conversation can sustain multiple tool calls plus reasoning. The guard trims heavy arrays (edges → nodes → results → tags → backlinks → outgoing_from_start → backlinks_to_start) and appends `_truncated`. `get_graph_overview` default = compact summary (stats + top 20 hubs + orphan sample + top 10 tags, ~4 KB at any scale); `include_nodes: true` / `include_edges: true` are opt-in and size-guarded. `get_tags` default = top 50 tags with 50-page samples each. `get_connected_nodes` caps at `max_nodes: 60` (ranked by hop + degree), max depth 2, 120-char previews — enough to keep even hub-entity traversals under budget (e.g. `tali-rezun` at depth 2: 39 KB on the 2116-node articles domain).
- **MCP security** — defense in depth against LLM-driven path traversal. `storage/local.js` has a single `resolveInsideBase()` chokepoint that rejects absolute paths, `..` segments, and anything resolving outside the domains folder. Tools additionally validate their `domain`/`slug` args via `isValidDomain` / `isValidSlug` from `mcp/util.js` (strict alphanum+hyphen+underscore) for clean error messages. The `/api/mcp/reveal-config` endpoint uses `execFile` (not `exec`) so no shell interpretation. **The MCP is NOT read-only** (it was, up to v2.5.1; write tools landed in v2.5.2 — see the read+write-client bullet below). Seven tools mutate user data — `compile_to_wiki`, `fix_wiki_issue`, `dismiss_wiki_issue`, `undismiss_wiki_issue`, `save_working_state`, `save_project_brief` (v3.48.0; writes the standing brief ONLY on the user's instruction, with a provenance comment), `save_foundation` (v3.59.0; writes ONE canonical document whole, only with `commissioned_by_owner: true`; gains an optional TRI-STATE `read_first` in v3.62.0 — omitted must reach the store as `undefined` or every ordinary save silently unmarks the document) — and `fix_wiki_issue` can **delete** files (`crossFolderDupes` / `hyphenVariants` / `semanticDupe` all `rm()`). Each of those seven, and only those seven, calls `refuseIfReadonly()` before doing any work, so a Shared Brain `shared-*` mirror is refused. **Enumerate the call sites across `mcp/tools/**` rather than trusting this sentence** — it said "four ... and only those four" through the whole of v3.17.0, three bullets below its own correct count of five, and cited line numbers that had rotted by three. Any new mutating tool MUST add that call.
- **MCP graph cache** — `buildGraph()` caches per-domain with a 10-minute TTL and a cheap dirent-only file-count check taken BEFORE the TTL early return (measured: 173 ms for a full listing vs 1.5 ms for the count on 3,000 files). A count change forces a rebuild; because an UPDATE leaves the count identical, every MCP mutator also calls invalidateGraph(domain) — derive that list from the refuseIfReadonly call sites. Before v3.40.0 the count check sat after the early return and was unreachable inside the TTL.
- **Model-lifecycle policy (v2.4.0; active-provider rules rewritten v3.45.0)** — single chokepoint for all LLM calls is `generateText()` in `src/brain/llm.js`, which dispatches to whichever provider is ACTIVE. **How a provider becomes active (Option B, v3.45.0):** saving a key sets it **only when nothing is active yet**; thereafter the writer is **choosing the build model**, and a key save leaves the lane where it is. Disconnecting the active provider falls to the **cheapest measured connected** provider, and records an explicit `null` when every candidate is refused rather than leaving the field absent for the legacy ladder to re-infer from. `ACTIVE_PROVIDER_DERIVED = false` in [src/brain/config.js](src/brain/config.js) restores the old last-saved-wins behaviour. Default models are pinned in `DEFAULTS`; `FALLBACK_CHAINS` provides an ordered next-best list per provider. On model-not-found errors (and ONLY those — 429/503 still retry) the chain is walked in order; the successful model is recorded in a module-level `_activeFallback` and surfaced to the UI via `getFallbackStatus()`. When a provider retires a model: bump the `DEFAULTS` constant, optionally add the old primary to `FALLBACK_CHAINS`, push a release. Users on older versions keep working via the chain until they Check for Updates. Full user/developer guide: `docs/model-lifecycle.md`.
- **Self-test isolation** — `POST /api/mcp/self-test` spawns `mcp/server.js` locally, sends initialize + tools/list + list_domains over stdio, and reports round-trip results. If this passes but Claude Desktop still can't see the tool, the issue is in `claude_desktop_config.json`, not the bridge.
- **Semantic-duplicate scan is opt-in, cost-gated, and scale-capped (v2.4.5+)** — never runs as part of the regular Health scan. The flow is: estimate → confirm dialog → SSE-streamed real scan → per-pair Preview → Merge. Three hard caps in code: `SEMANTIC_DUPE_MAX_DOMAIN_PAGES = 20000` (refuses larger domains), user-configurable candidate-pair cap (default 500), user-configurable cost ceiling (default 50k tokens). **Batch merge is offered for HIGH-confidence pairs only** (`fixSemanticDuplicatesBatch`, `src/brain/health.js:1205`, added v3.0.1-beta.15): an explicit confirm step names how many pages will be deleted, merges run sequentially server-side (never in parallel — each merge rewrites links domain-wide), the route caps at 2,000 pairs, and — since every change lands in the git-tracked wiki — a user with Personal Sync configured can recover with a git client. **There is NO in-app revert: `src/routes/sync.js` has never exposed one**, and claiming otherwise on the panel that launches a page-DELETING operation was a false safety promise found at 14 sites and corrected in v3.9.1. **Medium- and low-confidence pairs are still one-at-a-time behind the mandatory Preview-diff gate** — they are the ones most likely to be genuinely distinct, and a wrong batch merge across thousands of pages is the most expensive mistake in The Curator.
- **Destructive-merge safety gate (v2.4.5+)** — Phase 3 is the first and only feature that DELETES files. The Merge button is disabled until the user opens the Preview-diff modal for that specific pair, which shows exactly which files will change, how many links will be rewritten, and what the merged content will look like. The frontend tracks previewed pairs per session; new sessions require re-preview.
- **AI Health is READ-ONLY (v2.4.3+)** — `src/brain/health-ai.js` proposes fixes, it never writes. All mutations still go through the existing `fixIssue()` in `src/brain/health.js` via `POST /api/health/:domain/fix`, so the AI layer cannot corrupt the wiki even if the LLM hallucinates. AI suggestions are additionally validated against the on-disk slug set before being returned to the UI; unknown slugs are coerced to `target: null`. This invariant must be preserved for Phase 2 (orphan rescue) and Phase 3 (semantic duplicates).

A **transient** provider error (structured `err.curatorTransient` tag from `llm.js`, never a bare `/\b429\b/` — that also matches ingest's own `"yielded only 429 characters"`) pauses the whole batch; anything else fails one item; and a **consecutive-failure circuit breaker** bounds the harm regardless of classification. A recovered job comes back **`paused`, never running** — nothing may auto-start spend. `toWire()` is an explicit **allow-list** with length caps and path scrubbing; never reintroduce a `...rest` spread. A `budgetUsd` that cannot be priced is **refused (400)**, never silently accepted — and the cap guarantees spend is *tracked and bounded*, not that it is never exceeded. The estimate quotes a multiple **computed for the batch in front of it**; the fresh-vs-mature ratio is size-dependent (**39.4× at 2 KB → 2.1× at 80 KB**, with a step at ~15,000 chars where a source crosses to multi-phase) so **never hard-code a single multiplier** — a test asserts the multiple must move with document size.
- **Memory-layer (working state) invariants (v3.17.0+, hardened v3.17.1–.2)** — **state SUPERSEDES; knowledge ACCUMULATES**, and that is why there are two stores rather than one. The wiki's merge unions bullets, so a blocker resolved on Tuesday would be resurrected by Wednesday's write; a union merge cannot express *no longer true*. **`state/` therefore never goes through `writePage`** — and could not, even if wanted: `normalizePath` redirects every non-canonical folder and FLATTENS to the basename, so `sessions/projA/main/state.md` and `sessions/projB/feature-x/state.md` BOTH land on `entities/state.md`, the second silently overwriting the first. `(project, scope)` is inexpressible through that path. **The `<machine>` segment is load-bearing and must not be collapsed or 'simplified':** Personal Sync resolves with `git pull --no-rebase -X theirs`, which on a conflicting hunk silently discards the local side and reports success, so per-machine paths mean no hunk ever conflicts. It is `<hostname-slug>-<install-id>`, never a bare hostname — two clones sharing a default macOS name destroyed a handoff and its journal. **That argument covers tiers 2 and 3 ONLY:** `state/project.md` has no machine segment, so two machines editing the standing brief DO produce the conflicting hunk — the one place the guarantee does not hold, and `docs/sync.md` carves it out. **Single writer (tiers 2 and 3):** agents write handoffs and journals over MCP; the app is READ-ONLY over them, deliberately — a browser write path would make the app a SECOND writer and break the property the whole sync-safety argument rests on, and would stamp a human edit with the last agent's provenance. **Tier 1 is the human's (v3.48.0):** the standing brief is hand-authored, edited in the app (Domains → Projects), or written by an agent ON THE OWNER'S EXPLICIT INSTRUCTION through `save_project_brief`, which prepends a provenance comment read back as the authority value `commissioned` — the owner's framing, never untrusted. **Curator-owned tier 0 joined the human's write surface too (v3.61.0):** `initFoundations`, `saveFoundation` and `removeFoundation` are reachable from `routes/memory.js` for a `curator`-owned project ONLY — a `repo`-owned document is never written there, only mirrored — restating the single-writer property precisely: it was never "one PROCESS may write", it is "one writer per FILE, with provenance that matches" (a human write stamped `authoredBy.kind: 'human'`, structurally incapable of landing on a mirror because ownership is checked in the store before any write reaches disk); see `docs/working-state.md`'s human-edit-surface section for the full four-part argument and `docs/sync.md` for the no-machine-segment cost this extends from `project.md`. **The GITHUB MIRROR ARM (v3.63.0) does not weaken that argument, and `repo.remote` finally has a writer:** the field has existed since v3.59.0 and was only ever carried through or defaulted to null; it is now `{owner, repo, ref, path}`, and a non-null value is what makes a mirror a REMOTE mirror — `ownership` stays `repo`, so one-ownership-per-project is untouched. The arm changes WHERE the bytes are read from and NOTHING about who authored them: still a byte copy, still the repository as author. Three of its additions are refusals, not powers — `src/brain/github-read-client.js` can issue no verb but GET, a truncated tree refuses BEFORE the first blob is fetched, and NOTHING is written until every blob is in hand, so a failed read leaves the mirror exactly as it was. **The token is read from a FILE, never from a caller's argument** (`tokenSource`: `config` = `githubReadToken` in `.curator-config.json`, the recommended fine-grained read-only token, or `sync` = Personal Sync's PAT, never the default because a CLASSIC sync token can read every repository the user owns and that permission was granted for something else); a `token` in an HTTP body is not read, here or in the store. It is never logged, never in a URL, never in a thrown error — errors name the token's SOURCE. The read client is reached by DYNAMIC import because `test-tray-summary.js` walks the store's static import graph to prove the menubar widget can reach no fetch site. **Freshness is not compared over the network on a READ** — only inside a refresh, an action with a button — so `remoteChecked` is always false off `listFoundations`, which is how a surface tells "nobody asked GitHub" from "GitHub says it is current". **`readFirst` (v3.62.0) is the case that makes "one writer per FILE" do real work, so read it as the test of that sentence rather than as an exception to it:** `setFoundationReadFirst` is reachable on **EITHER** ownership (`PATCH …/foundations/:slug`) because it writes `foundations/manifest.json` and **NOTHING else** — the flag is CURATOR METADATA ABOUT a document, never part of it, so every mirrored `.md` stays byte-for-byte the checkout's and `sha(stored) === sha(source)`, the claim the whole freshness reading rests on, is untouched; the manifest is ALREADY app-written on a mirror by `…/foundations/refresh` and by v3.61.1's `DELETE`. It was NOT built as an arm of `saveFoundation`, which is refused `ownership-mismatch` on a mirror — the contract asked for the PUT and the builder refused, correctly, because a repo-owned project would then have had no way to flag anything from the app at all. `readFirst` is **TRI-STATE** on `PUT` and on `save_foundation` (`undefined` PRESERVES, only an explicit boolean moves it) — the OPPOSITE default to `skeleton`, which a save clears, and the difference is that `skeleton` is a fact about the TEXT while `readFirst` is an instruction about the DOCUMENT; normalising an omitted field to `false` would un-route a document on every text edit. A mirror refresh PRESERVES it. The two budgets are **named apart and must stay so**: `FOUNDATIONS_BUDGET_BYTES` (200 KB, the PROJECT's disk budget) vs `CONTEXT_MAX_BYTES_DEFAULT` (120 KB, the BOOTSTRAP's reading budget), and `readFirstReadings` measures the flagged set against the SECOND — collapsing them makes a surface say "within budget" about the wrong budget. **Projects inside a domain (v3.48.0):** a domain hosts many projects, each with its own brief and scopes under `state/<project>/…`; the domain's OWN project lives at the state root PERMANENTLY (never `state/<domain>/`, because `state/` syncs and a mixed fleet would read a fresh domain as empty) and can be neither renamed nor deleted; `list_projects` + a bare project name in `get_working_state` resolve across domains with ambiguity returned as candidates, never guessed; `scope: "latest"` opens the newest work-stream; the `.curator-project` marker is read by the SKILL, not the server. **THE CLI IS A SECOND WRITER OF TIERS 2–3, AND IT IS THE TEST OF "ONE WRITER PER FILE" RATHER THAN AN EXCEPTION TO IT (v3.63.0):** `my-curator save` (`bin/curator.js` → `src/cli/save.js`) calls the SAME `saveWorkingState` the MCP tool calls, writing the same `(project, scope, machine)` path with provenance `kind: 'agent'` and `harness` from `--harness` — so the file has one writer with matching provenance, which is what the rule has always said. It is a second LOCAL CLIENT, exactly as `mcp/server.js` is; it is NOT the app. **The app still never writes tiers 2 or 3**, and the structural guarantee is that no Express route calls the CLI and `src/routes/**` imports neither `bin/**` nor `src/cli/**` — a browser-reachable save would stamp a human edit with an agent's provenance and make the app the second writer the whole sync argument forbids. **A hook never composes a handoff** (`src/cli/hook.js` does not call `saveWorkingState` at all): it may ask, inject or record, and it asks the MODEL to call the tool, because a fabricated handoff is worse than a missing one. **Capture is skill-instructed and ADVISORY** (`claude-skills/curator-continuity/`): nothing forces a save, and a missed one yields the PREVIOUS state, never a corrupted one — the fail-safe direction, and the reason no enforcement was added. Saving OVERWRITES and is therefore idempotent, so the instruction is **save early and often**, and **every save must be COMPLETE, not a delta**, or the third save silently drops the firm decisions recorded in the first. **An over-budget save is TRIMMED and disclosed in `notes`, never refused** — an agent near its context limit whose handoff is rejected loses it entirely. **Counts are taken BEFORE the index slice:** `distinctScopeCount` counts distinct scopes over the UNCAPPED pair list, because deriving it from the capped array reports a CAP as a measurement. **`scopeCount` is a LEGACY name meaning two different quantities** — distinct scopes on `GET /api/memory`, the (scope, machine) pair total on `GET /api/memory/:project` — both pinned by different suites, so neither was redefined; read `distinctScopeCount` and `savedCopies`, which mean one thing each everywhere. **`resolveInsideState` is the sole path chokepoint.** Sanitisation runs on READ as well as write, and defang **never deletes** — a legitimate handoff routinely carries URLs and commands. **The dominant defect class here is a consumer silently dropping a field the store honestly computed** (`unlistedEntries`/`unlistedReason`, `requestedMachine`, `machineIsThisHost`, `installIdAvailable`): guarded BEHAVIOURALLY by `scripts/test-working-state-disclosure.js`, never by a name scan — `res.json({ ...state })` and `out.current = state.current` forward fields wholesale, so a text search reports drops that are not real and misses real ones. **Chat joined the readers, never the writers (v3.64.0):** `src/brain/chat.js` is a READ-ONLY in-process consumer of tiers 0–3 through `getProjectContext` — called directly, no route hop — under its own separate `PROJECT_CONTEXT_BUDGET_CHARS` (40 KB) budget, additive to the wiki's own; it writes nothing to any tier. **`knowledgeDomains` joined the human's write surface in v3.65.0, on the SAME footing as `readFirst`:** `state/[<project>/]project.json` is curator metadata ABOUT a project — which wikis its knowledge lives in — never state, so `PATCH …/knowledge/domains` is a legitimate APP write (not a second writer of tiers 2/3, and not tier 1 either): an agent never touches the file, proven by execution rather than by comment, and absent reads as the containing domain with `knowledgeDomainsDefaulted: true` rather than an empty list. **The GitHub mirror arm's REMOTE-BORN case (v3.65.0) preserves the token-from-a-file rule exactly:** `POST …/foundations/init` accepts `remote` + `tokenSource` naming which FILE on this computer already holds a read-only token — never a token in the request body, refused by name if one arrives — so a mirror created with no local checkout reads a credential the same way `…/foundations/refresh` always has, through `src/brain/github-read-client.js`'s GET-only surface. **A mirror's SOURCE can be RE-CHOSEN without ever touching ownership (v3.65.1):** `setFoundationsSource` re-points an existing repo-owned project at a different GitHub repository — clearing `repo.root`, setting `repo.remote`, and preserving every `readFirst` flag by slug, all in the SAME `writeManifest` the refresh path already performs — while `ownership` stays `repo` and ONE SOURCE PER PROJECT holds throughout (a folder or a repository, never both at once as the live source); it is refused on a curator-owned project before any network read begins, and its token is read from a FILE the caller only NAMES (`tokenSource: 'config' | 'sync'`), never a value the caller supplies, extending rather than relaxing the rule two sentences up.

## Known benign GitHub behaviours

- **"Sorry, we had to truncate this directory to 1000 files"** on GitHub's web UI when browsing `domains/articles/wiki/concepts/` (or similarly busy folders) is a **GitHub rendering limit, not a sync issue**. Git itself handles millions of files per directory; the truncation only affects the file-listing view on `github.com`. Clone the repo locally, or use `git log` / `git ls-files`, and you see everything. Sync push/pull transfers all files correctly regardless of this UI limit.

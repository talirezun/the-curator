## Wiki write pipeline and Health

- **CLAUDE.md per domain** — each domain is a specialist, not a generalist. The schema shapes how the LLM categorises knowledge for that domain.
- **syncSummaryEntities is idempotent** — safe to run multiple times; injectBulletsIntoSection deduplicates by link target.
- **deduplicateBulletSections is always safe to run** — only removes bullets whose dedupKey already appeared earlier in the same section; never drops unique content.
- **The press rule: Wiki health answers where you pressed (Stage 1 of the redesign, `views/domains.js` "THE PRESS RULE" and `shared/row-motion.js`)** — the pressed control changes its own label within a frame at a locked width (`pressLocks`) and is `aria-disabled`, not `disabled`, so it keeps focus; a question, plan, ring and outcome line draw in one stack under the row that opened them (`pressAnchor`, `renderAnchorStack`, re-homed each paint by `healthStackHome`, so nothing is stranded); an action sets the plain field `state.rowNote` and `render()` files it (`takeHealthNote`), which keeps the actions free of new identifiers because suites lift them, the merge gate's proof among them. **The Health section has no banner**; `state.banner` is the page's own notices, drawn above ⑤. A leaving row is copied back into the next paint (`holdLeavingRows`), held about a second, then collapsed with the Web Animations API: no `transitionend`, no inline style a patch would strip, and under reduced motion it is held and removed at once. **A row above the press never moves it:** a row a reading settled stays, dimmed, "Resolved", and a new one waits hidden, until a press above it, its fold being touched, or a scroll (`releaseHeldRows`). Scroll is held at the page's end by a floor under the section (`createScrollFloor`, a CSS variable on the scroller, because a patch would strip a style off the section). A failure stays on the row with Try again until acted on. Above Health, the Ingest section's "Waiting on another write" note now shows only when a file is chosen: with none it explained nothing, and it pushed the whole page down 99 px for every repair. **An outcome belongs to the domain it ran on:** an action records `state.rowNoteFrom = { slug, token }` with its note, and one for a domain or mount no longer on screen waits as a line (`rowAway`) and touches nothing on screen. **A delete warning states a count read at that moment** (`readHealthBeforeAsking`); no report, no question. `checkedAt` on the health route is when the wiki was last looked at, beside `scannedAt`, when it was read (a cache hit keeps the older one); the view shows `checkedAt`. On the app's route, a page writing one broken link twice is one row with `occurrences`, matching the dismissal key (`collapseRepeatedLinks`); `scanWiki` and the MCP still list occurrences, and a fix-all's `distinct` says how many links its `total` were. The section head's trace holds only short fixed words and is never cut: whole sentences belong on the row or its line. A quiet reading (a silent reload, or a rescan behind a kept report) keeps the pair list but empties `previewed`, so Merge is disabled again until previewed: a repair may have changed the pages a preview showed. Measured by `scripts/e2e-wiki-health.mjs` (stage `s1`); the logic is `scripts/test-next-press-rule.js`.
- **A free repair that deletes nothing does not ask (owner's decision, 2026-11-05; reverses v3.x "every Fix all is gated")** — `confirmFixAllOfType` and `confirmFixSafe` run at once unless a page would be deleted (`DESTRUCTIVE_FIX_TYPES`, `safeFixDeletedPages`). The old reason was that an inconsistent gate makes a destructive click feel safe; the words now carry that difference: the deleting confirm counts the pages and its button says "Merge and delete". Anything deleting a page still asks, and the merge comparison gate and the server-checked batch are untouched. Suites changed deliberately: `test-next-summary-link-view.js` §3 and `test-domains-true-numbers.js` 8.3 assert the run on the press; `test-health-merge-links.js` §9 still holds for the deleting types.
- **Semantic-duplicate scan is opt-in, cost-gated, and scale-capped (v2.4.5+)** — never runs as part of the regular Health scan. The flow is: estimate → confirm dialog → SSE-streamed real scan → per-pair Preview → Merge. Three hard caps in code: `SEMANTIC_DUPE_MAX_DOMAIN_PAGES = 20000` (refuses larger domains), user-configurable candidate-pair cap (default 500, per RUN), user-configurable cost ceiling (default 200k tokens as of v3.72.1, up from 50k — the old default undercut the 500-pair cap it was meant to pair with). **Batch merge takes only a spelling variant with a remembered high-confidence answer** (`fixSemanticDuplicatesBatch`, `src/brain/health.js`, added v3.0.1-beta.15, narrowed when measured "high" answers proved wrong): an explicit confirm step names how many pages will be deleted, merges run sequentially server-side (never in parallel — each merge rewrites links domain-wide), the route caps at 2,000 pairs, and — since every change lands in the git-tracked wiki — a user with Personal Sync configured can recover with a git client. **There is NO in-app revert: `src/routes/sync.js` has never exposed one**, and claiming otherwise on the panel that launches a page-DELETING operation was a false safety promise found at 14 sites and corrected in v3.9.1. **Every other pair is one-at-a-time behind the mandatory Preview-diff gate** — a wrong batch merge across thousands of pages is the most expensive mistake in The Curator.
- **A duplicate scan remembers its answers; the wiki is not where (`src/brain/duplicate-checks.js`)** — one JSON file per domain at `paths.js getDuplicateChecksDir()` (`<user data>/.duplicate-checks/`), outside `domains/`, gitignored, in `DOMAINS_GITIGNORE_RULES`, written atomically after EACH batch. A cache: missing or corrupt reads as empty, and a failed save only logs to stderr. An answer applies while the pair (FOLDER + slug, either order: a slug pair alone would apply one page's answer to another), provider, model, sha of the system prompt and sha of the two openings are unchanged. The prompt hash is there so tightening the rules re-checks old answers with no version to remember. `findSemanticCandidatePairs` knows nothing of answers; `planSemanticScan` layers over it, and only what will really be sent is estimated, ceiling-checked and confirmed. Nothing to send means no provider call. A valid index with a valid relation always remembers something, because a measured third-name canonical otherwise re-billed one pair on every scan (`semanticKeepSlug` picks a deterministic side). A batch failing on the output limit or an unusable reply splits in half, at most two levels (`judgeBatch`); auth, quota, rate-limit and network errors do not. A reply with no `results` array is a FAILED batch (`jsonrepair` turns prose into a JSON string, so "it parsed" is no answer). `liveCandidates` keeps the last derived list for one domain, keyed on the page names and dismissals, the only inputs it has.
- **The scan asks for a relation, and the names it can offer are the names it can merge** — a yes/no prompt accepted 765 of 2,000 real pairs on Flash Lite, so the prompt asks for `difference` and `relation`, and only `same` is a yes (measured table in `docs/ai-health.md`; the system text is the measured one, verbatim, and its hash re-checks old answers). An unknown relation remembers nothing. The batch output limit is 6,000 because Haiku overflowed 2,048. `isMergeableSlug` is the ONE name test for the candidate list and `resolveSemanticDupePair`: the old regex refused an underscore the list offered, so a card could show a Merge it could not perform. It still refuses anything that could leave the folder or that a wikilink cannot carry, and `resolveInsideWiki` still follows.
- **Batch eligibility is the server's, and it never reads the client's confidence** — `batchRefusals` decides before the first merge, because an earlier merge legitimately rewrites a kept page's opening (its link repoint can reach the opening of any page). Spelling-variant test (`isSpellingVariant`): equal after removing separators and lower-casing, or differing by a final plural. A separator between two digits is kept (`gpt-4-1` ≠ `gpt-41`); plurals refuse a stem ending in a digit or under 4 letters (`iphone-14s`, `news`). The view reads `spellingVariant` from the server and holds no copy of the rule. Single merges and the MCP's `fix_wiki_issue` are unchanged, behind their Preview. `window` / `windows` passes the name test, so only the model's answer guards that shape.
- **A merge that deletes a page never loses text (`src/brain/page-merge.js`)** — `composeMergedPage(keep, remove, {sourceLabel, keepFolder})` is the ONE composer, used by `fixSemanticDuplicate`, `fixHyphenVariant`, `fixCrossFolderDupe`, the preview and the manual repair scripts (`repair-wiki.js`, `fix-wiki-duplicates.js`, `fix-wiki-structure.js`). It replaced `mergeBulletSections` and "longer page wins": no archived row gives a reason for that rule beyond the v2.2.0 first draft, and it silently discarded the shorter page's opening and every non-bullet section, under the kept name when the removed page was longer. The kept page is the base and its lines are not edited, apart from tags (union) and `type` (follows the folder, now only inside frontmatter, where the old replace also rewrote `type/concept` in body text). A top-level bullet under a same-named `##` joins that section; one of the eleven accumulating names is created if missing; everything else goes under `## Merged from <slug>` (`<folder>/<slug>` when the slugs match). **Headings under it drop one level deliberately:** `extractSectionMap` ends a section at `#`, and an incoming `## X` replaces an existing one, so verbatim headings would lose moved text on the next ingest. **A bullet whose first link matches a DIFFERENT kept bullet goes under `## Merged from`, not the section:** `dedupKey` would drop it at once, and `deduplicateBulletSections` on the next writePage if it were placed there. "Already there" means the same lines, consecutive, in the kept body, which is what makes a second merge return its input byte-identical. The tokenizer is fence-aware (a `## x` in a fence is not a heading) and treats a table or paragraph as one block. `findLostLines` is a second check that shares no tokenizer: any line missing means `{ok:false, reason:'merge-would-lose-text'}` and no write, no delete. `isSameFile` (`merge-same-file`) refuses a delete when both names reach one file (a case-insensitive disk, a kept name that is a link to the removed file, a crafted `keep === remove`). `previewSemanticDuplicateMerge` applies the same `composeMerge` and the same `retiredLinkRewriter`, so `mergedPreview` is the bytes on disk. Proof: `scripts/test-merge-keeps-all-text.js`. **Not fixed, and outside this path:** a first write's `deduplicateBulletSections` still keys prose bullets on their first link, and `extractSectionMap` is fence-unaware, so a column-0 `# x` inside a code block on a page ends a section for a later ingest. Merges before this fix lost text that only git history can return.
- **Destructive-merge safety gate (v2.4.5+)** — Phase 3 is the first and only feature that DELETES files. The Merge button is disabled until the user opens the Preview-diff modal for that specific pair, which shows exactly which files will change, how many links will be rewritten, and what the merged content will look like. The frontend tracks previewed pairs per session; new sessions require re-preview.
- **AI Health is READ-ONLY (v2.4.3+)** — `src/brain/health-ai.js` proposes fixes, it never writes. All mutations still go through the existing `fixIssue()` in `src/brain/health.js` via `POST /api/health/:domain/fix`, so the AI layer cannot corrupt the wiki even if the LLM hallucinates. AI suggestions are additionally validated against the on-disk slug set before being returned to the UI; unknown slugs are coerced to `target: null`. This invariant must be preserved for Phase 2 (orphan rescue) and Phase 3 (semantic duplicates).
- **Conversation compile reuses the ingest write pipeline (v2.5.0+)** — `src/brain/compile.js` imports `writePage`, `syncSummaryEntities`, `appendLog` from `files.js` and runs the same Pass A/B/C link normalisation, cross-folder dedup, hyphen-variant resolution, and summary-backlink injection that ingest gets. Compile and ingest therefore share **one** page-composition write path, and the MCP `compile_to_wiki` tool (v2.5.2+) reuses the same module via direct import rather than re-implementing it. **Scope, stated precisely — this is NOT "one write path for the whole app":** `src/brain/health.js` does not import `writePage` at all. Every Health fix writes markdown directly via `writeFileAtomic` (`health.js:584, 595, 618, 652, 1167, 1171, 1178, 1300`) and deletes with `rm()` (`:619, 650, 1181`) — no frontmatter injection, no `mergeWikiPage`, no Pass A/B/C link normalisation. Health's own chokepoints are `fixIssue()` (dispatch) and `wikiFile()` → `resolveInsideWiki` (path construction, v3.2.0). **Treat `health.js` as a second, independently-guarded write surface when auditing:** v3.2.0's CRITICAL — a symlink escape that could DELETE a file outside the wiki — lived there precisely because it builds its own paths, and a doc claiming a single chokepoint is what stops an auditor looking.
- **Compile slug is deterministic and idempotent (v2.5.0+)** — summary path = `summaries/<slugify(title)>-<YYYY-MM-DD>-<4hex(corpus)>.md`. Same conversation, same date, same content → same slug → file existence check refuses re-compile with a clear message ("Already compiled to X. Send another message to extend it, or delete that file to start over"). Adding a turn changes the corpus hash → new slug → no collision → compile proceeds normally. This file-existence-as-state design avoids any side state in the conversation JSON and carries cleanly into the v2.5.1 MCP tool.
- **Compile does NOT regenerate index.md via the LLM (v2.5.0+)** — on a 2000-page domain the index is 20 KB of markdown table; asking the LLM to rewrite it on every compile saturated the JSON output budget and broke parsing on the second click against `articles`. `mergeIntoIndex()` in `compile.js` reads the existing index, appends rows for any pages this compile actually CREATED (not updates), and writes back. **Superseded by v3.83.0:** the created-only rule is gone — see the next bullet; `mergeIntoIndex` survives only as a compatibility wrapper. Sanitised against pipe/newline injection in cell content. Pages are paired with their summary by post-write canonical path so cross-folder dedup redirects don't drop the description column.
- **Every write path ensures every page it touched is in index.md; only Health rebuilds (v3.83.0)** — ingest, app Compile and the MCP's `compile_to_wiki` all call `ensurePagesInIndex()` (`src/brain/wiki-index.js`) after their writes. It adds a row for EVERY page the write touched that `index.md` does not list — created, updated or unchanged (the old rule appended created pages only, so any page that predated the merge stayed unlisted forever) — and it RE-READS `index.md` at merge time rather than merging into the copy read at the start (ingest reads at the start and merges at the end; a write in between used to be overwritten). Coverage is by CANONICAL path (a bare `[[x]]` resolves to `entities/` then `concepts/`, the Health rule), never by basename — a basename test hid projects' gaps behind 11 cross-folder slug collisions. A description comes from the model's page summary, else is derived from the page's first `# ` H1 or first body line (Curator pages carry NO `title:` frontmatter). Existing lines are never edited, removed or reordered; a sectioned index (`## Summaries` / `## Entities` / `## Concepts`, sorted by code unit) gets the row at its sorted position, a legacy single table after its last row. Pages whose file name cannot be linked (a leading or trailing space, or `| [ ] #`) and concepts shadowed by an entity of the same name are skipped, not mangled. Nothing removes a stale row on a write path; only the user can, through Health's Rebuild index.
- **Wiki health's three lanes (the redesign's Stage 2)** — one card, three lanes in cost order: Free repairs (no AI, no cost, no page deleted), Your decision, AI help; each drawn only when it has rows, or a trace. Quick maintenance is retired from this section; the kit keeps `renderActionCard`. **Repair all is client-run, never `fix-all-safe`**: that route also runs the two page-deleting types, so the lane posts one `/fix` per free type in the route's own order (`FREE_REPAIR_ORDER`); the route stays for its other callers. **Compare's cost is lazy on purpose**: its estimate needs the candidate pass (about 18 s on 3,500 pages), so it is read when the row is on screen or right after a count, the button waits for it, and what the confirm says is fetched again at the press. **Spelling variants stands above Possible duplicates**: a batch settles pairs in the list, and above the press they moved it by about 1,000 px. **Leave as is keeps the row in place with Undo** until the next Check again, so a list can be walked and nothing moves; Undo arms 500 ms late, so a double click does not undo. Words: `scripts/test-helpers/health-words.js` is the audit's table, and `OUTSIDE_THE_DECK` names each string the word deck lacks. Today's pair cards under Review keep their old words until the review desk. **Running state belongs to its domain**: `state.busyKey` speaks for the domain on screen and `parkHealthBusy` holds another domain's. **Merge never waits for a count**: the question opens from what is on screen and the read changes it in place. **A return shows what is known** (`state.cache[slug].health`, keyed by that slug, with "Checking…" in the head). **`pageOpening` stops at `## Merged from`**, so a merge does not lapse the kept page's answers.
- **The `indexDrift` Health check and Rebuild index (v3.83.0)** — Wiki Health reports **Index gaps**: pages on disk with no row, rows whose target does not exist, duplicate rows and repointable rows, counted as ONE issue. It is NOT auto-fixable (`AUTO_FIXABLE` is unchanged, so `fixIssue`, `/fix`, `/fix-all`, `fixAllSafe`, "Fix N safe issues" and MCP `fix_wiki_issue` can never touch `index.md`) and NOT dismissible (a fix-type row is never dismissible). It is skipped on read-only `shared-*` mirrors (their `index.md` is the creation stub, never maintained; `counts.indexCheck` is `'mirror'`). `index.md` is part of the scan-cache signature (`log.md` still is not) — without it a successful rebuild, which writes only `index.md`, would leave the cached "N missing" on screen. The repair is the user-triggered **Rebuild index** in Quick maintenance: `POST /api/health/:domain/index/plan` (read-only) returns a `basis` hash and a summary; `POST /api/health/:domain/index/apply` takes ONLY `{basis}`, re-plans from disk and writes only if the fresh basis equals the caller's (409 `INDEX_PLAN_STALE` otherwise) — the server never writes client-supplied index text. The rebuild is deterministic, no AI, free: existing descriptions kept byte-for-byte, missing ones derived, sections Summaries / Entities / Concepts sorted by code unit, stale rows removed, duplicates merged, repointable rows repointed. The `# Wiki Index — <name>` title form is kept (domain rename patches it by regex). Measured on the articles domain: 2,705 pages added, 39 stale rows removed, 767 descriptions kept, 146 KB → 614 KB. `planIndexRebuild` / `applyIndexRebuild` are on `health.js`'s guarded write surface (names bound to `wikiFile(...)`, `writeFileAtomic`).
- **`writePage()` returns structured change records (v2.5.0+)** — `{canonPath, status, bytesBefore, bytesAfter, sectionsChanged, bulletsAdded}` (or `null` on invalid input). Status is `created` / `updated` / `unchanged`. The `sectionsChanged` heuristic flags section names whose bullet count grew (good enough — byte-level `bytesBefore !== bytesAfter` plus the status flag still accurately tells the user "something changed"; deep diff is overkill). The shared `renderChangeRecords()` helper in `app.js` is used by both ingest and compile result panels — splits new/updated/unchanged with unchanged collapsed by default. Future MCP write tools (v2.5.1+) will return the same shape so Claude renders the same panel in chat.
- **Health dismissals are persistent and synced (v2.5.1+)** — `domains/<d>/wiki/.health-dismissed.jsonl` lives inside the wiki folder (already git-tracked), so dismissals propagate across machines via the existing GitHub sync without any sync-config tweaks. Format is one JSON object per line so concurrent dismissals on different machines append cleanly through git's standard 3-way merge. Order-insensitive identities (semantic-dupe pairs, hyphen-variant groups) are canonicalised on write — `{a, b}` and `{b, a}` produce the same `keyForIssue()` and one stored record. `loadDismissed()` runs a silent stale-record prune on every load (drops records whose referenced files/slugs no longer exist) so renames and merges don't pollute the file forever.
- **Summary link sections are filed by folder; `summaryLinkSections` is a guarded safe fix (v3.84.0)** — a summary lists entities under `## Entities Mentioned` and concepts under `## Concepts Introduced or Referenced`; `syncSummaryEntities` decides by the page's FOLDER (where `writePage` actually put it), never by what the model called it. `injectSummaryBacklinks` and the `missingBacklinks` scan read BOTH sections (so existing wikis show MORE missing backlinks right after updating — measured articles 4 → 338, projects 0 → 512 — and "Fix N safe issues" clears them). `writePage` de-duplicates a SECOND time after its link rewrites, and Health's rewriters call `dedupRewrittenBullets`. Health category `summaryLinkSections` (one row per summary: `duplicateLines`, `conceptsToMove`, `entitiesToMove`, samples) is in `AUTO_FIXABLE`, runs LAST in `fixAllSafe`, is not dismissible, is `[]` on `shared-*` mirrors and counts in `HEALTH_ISSUE_KEYS`. HARD GUARD: `summaryTidyGuard` refuses to write unless the page's link-target set and every non-blank line outside the two sections are unchanged (`link-guard`). Limits: only the first section with each heading is tidied; other headings ("Key Concepts") are not recognised.
- **Health dismissal scope (v2.5.1+)** — Dismiss buttons appear ONLY on review-only Health rows (orphans, broken links without a suggested target) and on semantic-dupe pair cards. Auto-fixable issues (`brokenLinks` with `suggestedTarget`, `folderPrefixLinks`, `crossFolderDupes`, `hyphenVariants`, `missingBacklinks`, `summaryLinkSections`) intentionally don't get a Dismiss button — the right action is Apply, not skip. If a user really wants to suppress one of those, they can dismiss it after the fact from the Dismissed section. This keeps the UI focused on "fix or skip" and prevents the auto-fix surface from becoming cluttered with skip-style affordances.
- **`normalizePath` special-cases index.md and log.md (v2.5.2+)** — pre-existing latent bug: `normalizePath('index.md')` returned `'entities/'` (no filename) because the second branch treated `'index.md'` as an unknown-folder name. The basename guard then refused the write silently. This had been masking ingest's index updates since v2.0; only surfaced when v2.5.2's MCP write path (which calls `writePage(domain, 'index.md', mergedIndex)` directly) made the symptom impossible to ignore. Fix: explicit early-return for `index.md` and `log.md` at the top of `normalizePath`.
- **Domains are siloed by default (v2.5.6+ documented; behaviour is implicit since v2.0)** — `compile_to_wiki` writes to one domain per call, ingest's slug inventory is per-domain, link grounding (v2.5.5+) only resolves against the current domain. Cross-domain reasoning happens at the MCP-read layer (`search_cross_domain`) — a Claude conversation can synthesise across domains without persistent cross-domain links being created on disk. Obsidian, when its vault root covers multiple domains, may surface accidental edges where slugs collide across domains; Health is per-domain so those show as broken in the source domain even though Obsidian shows them connected. Documented in full at [`docs/domains.md` § 4](../../docs/domains.md#4-how-domains-relate-to-each-other). Intentional cross-domain linking (e.g. `[[business:openai]]` syntax) is not currently supported — would require parser/scanner work in `health.js`, `compile.js`, and the MCP tools.

## Ingest

- **Ingest asks after writing: it records what it created, the scan compares those first (`src/brain/recent-new-pages.js`)** — one JSON file per domain at `paths.js getRecentNewPagesDir()`, outside `domains/`, gitignored, in `DOMAINS_GITIGNORE_RULES`: names only, oldest first, capped at `RECENT_NEW_PAGES_CAP` (2,000), missing or corrupt reads as empty, a failed write only logs to stderr. Written straight after the page-write loop, from `changes` with status `created`, concepts and entities only. **The order lives in `planSemanticScan` (`newPagesFirst`), never in `findSemanticCandidatePairs`**, whose output is pinned by a golden fingerprint; `live` stays in its old order, only `toCheck` and `send` change. A gone page cannot count, because the figures are read off the live unanswered list; its name leaves the file at the next ingest or scan. **The result's figure comes from `candidatePairsTouching`** (these pages x all pages, about 0.2 s for 20 on 3,500) rather than the 15 s triangle. That function repeats the full pass's test in a few lines, on purpose, so the golden path stays untouched, and `scripts/test-recent-new-pages.js` cross-checks the two: the lower index must go first, because `jaroWinkler` and the shared-token count are not symmetric (a mutation proved it). The one line in the result says names are close, never that pages are duplicates, and counts "N of M new pages" so it cannot contradict the change list above it. NOT RECORDED: pages from Compile, `compile_to_wiki` and another computer. Measured mean is about 21 pairs per page (36,332 x 2 / 3,407 on one domain), so the "only when there are candidates" condition rarely hides the line on a large wiki, and one ordinary ingest can fill most of the 500-pair default; old pairs, old spelling variants included, wait until new ones are answered. KNOWN: a dismissed pair across two folders stays a candidate in BOTH passes (record `folder: 'mixed'`), older than this work.

- **Apply a fix to the path that runs FIRST, not just the path you were looking at (v3.0.17+)** — v3.0.16's `extractPageArray` closed a silent-drop hole on the single-page FALLBACK while the batch path, which runs first for every batch of every multi-phase ingest, kept the original bug: `{"pages": []}` is truthy, so a whole batch's pages vanished with no stub, no warning, and a green result panel; `{"pages": {}}` threw `TypeError` and killed the ingest. When fixing a response-shape bug, enumerate EVERY call site that consumes that shape before declaring it closed.
- **`parseJSON` is lenient and its output must be validated, not merely truth-tested (v3.0.17+)** — it falls back to jsonrepair, which turns the bare text `not json at all` into the truthy STRING `"not json at all"`. An `if (!parsed)` check accepted that as a successful outline, skipped the retry, and `validateOutline` degraded it to a summary-only plan — an 80,000-char source could produce a ONE-PAGE wiki. Any `parseJSON` result that is supposed to carry a page list must go through `usablePageArray`/`extractPageArray`, never a truthiness check.
- **Repeated warnings aggregate at emission, and two classes deliberately do not (v3.0.17+)** — `aggregateWarnings()` collapses same-class entries at ONE chokepoint before the log entry is built, so `log.md`, the SSE payload and the result panel cannot disagree. Threshold is 3 (1–2 occurrences keep the specific path, which is the useful thing; 3 is the same "pattern, not incident" line the trunk-page detector uses), examples capped at 3 with "…and N more". A real run went 75 → 11. **Semantic near-duplicate notices ("Keeping both"; a spelling redirect is a `variant-redirect` and does aggregate) and trunk-page injections are excluded on purpose** — each names a specific pair or cluster the user must decide about; collapsing them trades signal for tidiness. When adding a warning that can fire per-page or per-batch, add it to the aggregator; when adding one that names a decision, do not.
- **The identical source again adds nothing to existing pages (owner's decision, 2026-11-06)** — the mostly-new test below slows re-ingest and cannot stop it: a model finds new vocabulary on every reading (+18,000 and +14,000 characters in rounds 2 and 3 on one domain, against a gate of about zero). So when `findCompletedIngest` (`raw-store.js`) finds these exact bytes already ingested into this domain, from any file name, `writePage` runs with `repeatSource`: every existing page stays byte-identical, frontmatter and link sections included, a fold too. New pages are still created (the one source of growth left: +1,139 and +929 characters on that domain, 0.06% a round), a stub is still replaced, the summary still gains links to new pages, and nothing is blocked: the same calls and the same spend, with one notice giving the count. **The record already existed, and could not be read as it stood:** `.raw-manifest.jsonl` holds the sha256 of each ingest and syncs, but its line was written when an ingest STARTS, so a provider failure leaves a record and no pages, and a retry would have added nothing. **The smallest addition:** a `completed` boolean, `false` on the start line and `true` on a second line written after the log entry. A record also needs its summary on disk, so deleting the summary starts again. A record older than the field counts on its summary alone; the one case that misjudges is a changed file whose ingest failed before the field existed, then retried. The hash is now awaited, about a second on a 126 MB file, and read before this ingest appends. **What this gives up:** re-ingesting an unchanged file no longer applies newer prompt rules to existing pages, or improves a thin one. Proof: `scripts/test-ingest-fold-keeps-text.js` §5c.
- **Exact-name reuse keeps the page, and adds new wording only when it is mostly new (owner's decisions, 2026-11-06; reverses "incoming prose wins", v3.0.1-beta.15)** — `composeReusedPage` (`src/brain/page-merge.js`). The page's text always stays, title and opening first. In any `##` section the incoming page repeats, wording that passes `isMostlyNew` goes directly below the kept text, verbatim; a new opening goes below the kept one; a section the page lacks goes at the foot if anything in it passes. **A first version kept every differing wording, and a live re-test killed it:** +50,000 characters and 600+ lines per re-ingest round on one domain, never converging, six near-identical definitions on one page. **The test, deterministic, no model call:** every sentence, list line, bullet or table is compared with ALL the words on the page, updated as text is added, after normalising case, punctuation, links (alias or slug words), stop words and a final plural. It joins only if at least `NEW_WORDING_MIN_SHARE` (0.5) of its content words are on no line of the page, or it holds a number the page lacks (`30 years` beside `25 years` shares every other word and is a new fact). **Measured on the replies of three live rounds, 79 lines labelled by one reader:** at 0.5, 86% of what is dropped is a real rewording and 92% of real new points are kept, 80% of rewordings caught; 0.45 gave 85/92/77, 0.55 gave 81/86/97, and the single closest line was no better than the whole page (0.7: 86/92/80, with more growth). Replayed through the real `writePage` on a copy of that domain: rounds 1, 2, 3 added 37,000, 18,000 and 14,000 characters, against more than 50,000 a round before; replaying all three again changed 0 pages; 0 existing lines lost. **It slows, it does not stop:** each reading finds some new vocabulary, which is why the identical source has its own rule (above); this one now governs a changed source and a different source. Known misses: a new point in the page's own vocabulary is dropped (4 of 49 in the sample; 17 of 19 new facts survived a live check), and a rewording with several new words is kept. So the notice never promises a new point was kept: it says what went and to compare the source with the page. **Every section has this rule**, because of what a copy of a 3,407-page domain shows: 812 distinct `##` names, and 10,294 of 36,121 bullet lines outside the accumulating list (How It Works 3,260, Key Aspects 890). **Link sections go by target** (Related, Entities Mentioned, Concepts Introduced or Referenced): a link-led bullet with a new target is always added, one with a known target never, whatever its description. Lines already on the page stay, repeats included. A fence is code: only an exact repeat goes. A sub-heading goes on the page only with something new under it. **Every drop is reported:** one `Page "x": N passages not added` line per page from `writePage`, aggregated at 3 (`reworded`), and the MCP's `compile_to_wiki` now returns `warnings`. An exact repeat is not reported; nothing was lost. **The guard changed with the rule:** step 5e still runs `findLostLines` on the final bytes, for every line of the EXISTING page on a reuse, of both pages on a fold, and a refusal writes nothing. Both pages are link-tidied BEFORE composing, or `[[concepts/x]]` would read as new wording. Summaries are included (`date` stays the first ingest's; the incoming `# title` is not text when the page has one). A differing frontmatter value goes in a YAML block under `## Frontmatter from a later write`. **Bullets on an existing page are no longer lost to the first-link dedup:** `dedupBulletsKeepingText` drops only a repeated line or a bare `- [[x]]` the section already names (also in `syncSummaryEntities`); a first write still uses `deduplicateBulletSections`. **A stub is the one exception:** a page holding the `Stub page` / `Stub summary` mark goes through `mergeWikiPage`, because its text says "re-ingest to fix". That and `reconcileGeneratedPages` (copies inside one reply) are all `mergeWikiPage` still does, which is why `test-beta15-fixes.js` still passes. Hub linkification writes with `replace` + `keepLines`: its text IS the page. **A fold is unchanged:** `composeMergedPage` moves everything, so a variant name reworded each round still grows. **No prompt changed:** no ingest or compile prompt says a section is replaced; the batch prefix and every recorded digest are untouched. A section cannot be corrected by re-ingesting or by `compile_to_wiki`: edit the file. Proof: `scripts/test-ingest-fold-keeps-text.js` §5, §5b (a fixed reworded corpus grows at most 10% by round 3; replay adds nothing), §10.
- **A page written onto an existing one under a name the model did not choose keeps the existing text; only a spelling variant folds (Stage 1 of stopping duplicates at ingest, owner's decision 2026-11-06)** — `writePage` calls this a fold when the NAME moved: Pass A, Pass B, step 3b, an underscore in the file name, or `opts.foldedFrom` from ingest's guard. A wrong folder, a nested path or a missing `.md` with the right slug is still ordinary reuse. A fold composes through `composeMergedPage` (`src/brain/page-merge.js`, existing page as the base), never `mergeWikiPage`, whose incoming base replaced the kept Definition, opening and title under a warning saying "merged". Step 5e runs `findLostLines` on the final bytes against both originals with the same link rewrites applied, and on any loss, or a composer that throws, writes nothing, warns and returns null: the kept page matters more than one proposed page. `dedupBulletsKeepingText` never drops a line nothing else in the section holds. A 0-byte page has nothing to protect. Summaries never fold (a re-ingest merges by design) and `opts.replace` (mirror pulls) never does. The same fold twice is `unchanged`, so compile stays idempotent. **`redirectSemanticDuplicates` folds on `isSpellingVariant` only, concept pages only.** It was Jaccard >= 0.85 on stemmed word sets, which on short slugs means an identical set, so it folded reorderings (`knowledge-domains` onto `domain-knowledge`, `security-in-ai` onto `ai-in-security`), and it dropped one-character tokens (`phase-2-build` onto `phase-1-build`, `plan-b` onto `plan-a`, at 1.00). All tokens count now, and a token with a digit is not stemmed; those pairs get the "Keeping both" notice or nothing. Measured reason: Haiku precision was 81% on anything looser, a wrong fold has no in-app undo, and a missed one costs one Health merge. The accepted cost: `experts-roundup-format`, this guard's own v3.0.1-beta.11 example, has its plural on the first word and now warns instead. `window` / `windows` passes `isSpellingVariant`, and here no model's answer stands behind it. A name holding `_` is not a target (writePage would rewrite it and create a new page), and a slug already on disk stays itself. Entities stay out of the plural rule (`jones` / `jone`). **The fold travels under a Symbol (`FOLDED_FROM`)**, which a model's JSON cannot set, on the plan entry (multi-phase, because the batch reply is a new object) or the page (single-pass). The Symbol never reaches a prompt: `buildBatchPromptParts` reads `path` and `summary`, so the prefix is byte-identical; prompts did not change at all. **A single-pass entry IS text:** two close names both reach the disk, and one path returned twice with different words writes the last copy as before and folds the earlier one on (multi-phase keeps keep-last, since a repeat there is a copy the batch was not asked for). A plan entry holds no text, so a plan naming a page and its variant has one entry, and it counts as ordinary reuse when the model named that page itself. Only `compile.js` and ingest pass `onWarn`; the MCP's `compile_to_wiki` reports a refused page only by leaving it out of its result.
- **The batch prompt's stable prefix is load-bearing — never let it vary per call (v3.0.16+)** — `buildBatchPromptParts` returns `{prefix, suffix}` and the ENTIRE cost win of v3.0.16 depends on `prefix` being byte-identical across every batch of one ingest. Anything per-call in it (a timestamp, a counter, Set/Map iteration order, or moving the page list back out of `suffix`) silently turns every cache READ into a cache WRITE at 1.25×, making ingest **more expensive** — with no error, no warning, and no offline test able to see it. The only proof is a live multi-batch run showing non-zero `cachedReadTokens` (Anthropic) — verified at write=41,822 / read=250,932 = 56.6% saving. Anthropic caching is gated BOTH by a size floor (`ANTHROPIC_CACHE_MIN_PREFIX_CHARS`, because Haiku 4.5 silently declines to cache under ~4,096 tokens) and by `totalBatches >= 2` at the caller (break-even is two calls); single-pass must never get a breakpoint.
- **The broken-wikilink rate is not a valid single-run gate (v3.0.16+)** — measured on UNMODIFIED v3.0.15 against an md5-frozen source and a fixed articles-scale domain, it ranges **Gemini 0.0–3.8%** and **Anthropic 2.4–6.1%**. That noise is wider than any effect a prompt change is likely to have, so an A/B at n=1–3 will confidently report an improvement or a regression that does not exist (this happened twice in the v3.0.16 work, in both directions). Use paired runs with several replicates per arm, compare against the paired baseline rather than the fixed 1–5% band, and — where the question allows — prefer **byte-identity of the generated prompt** over a statistical argument: it is deterministic and settles in seconds what 14 live ingests could not.
- **Ingest warnings are the contract for anything the pipeline silently changed (v3.0.16+)** — `writePage`'s `opts.onWarn` and `reconcileGeneratedPages` exist because two failure modes were losing user-paid-for content with only a `console.warn`: a page path missing `.md` was discarded outright, and a Phase 2 response returning a non-canonical `summaries/` path created a SECOND summary, permanently breaking that source's re-ingest idempotency. Rule: if the pipeline drops, redirects, renames, or flattens something the model produced, it MUST push a user-visible entry into `warnings[]` — a stderr line is not a user surface. `validateOutline`'s guarantees bind the OUTLINE only; anything Phase 2 returns must be re-validated against the paths that batch actually requested.
- **The index.md in the outline and single-pass prompts is capped (v3.83.0)** — the FULL index is pasted into both prompts (`buildOutlinePrompt`, `buildPrompt`), so a COMPLETE index is the next term to bound after the slug inventory: the articles index rebuilt is ~614 KB, ≈146k+ tokens at the 3 chars/token the code assumes, which with the slug inventory and the source exceeds Haiku 4.5's 200k window and would hard-fail every articles ingest. `indexForPrompt(index, sourceText)` runs INSIDE both builders (so ingest, the strict retries, the queue's cost estimate, the OpenRouter qualifier and the dev scripts all see the same prompt) with `INDEX_PROMPT_BUDGET_CHARS = 150,000` — just above today's largest index (projects, 146,744 chars). At or under the cap the SAME string comes back and every prompt is byte-identical to before (42 of 42 real-domain prompts measured identical). Over it: every non-row line (title, Last updated, headings, table header) is kept, page rows are ranked by token overlap of slug words + description with the source (coverage first, then match count, then original order), the top rows that fit are rendered in ORIGINAL order, and one trailing line says `(Index shortened for this prompt: N of M pages …)`. The slug inventory stays uncapped, so link grounding is unaffected. Policy: stderr line `[ingest] index shortened for prompt: kept/total` once per ingest and NO user-visible warning, because nothing the MODEL produced is dropped (the warn-on-drop rule above is about model output). Window arithmetic: 64,000 (one slug list at its cap) + 50,000 (index cap at 3 c/t) + 5,000 + 1,000 + 64,000 = 184,000 < 200,000; do NOT lower `SLUG_INVENTORY_BUDGET_CHARS`. Not measured: whether a capped index moves the broken-link rate. Side effect: the qualifier's default domain (`largestDomainByIndex`, the largest `index.md`) flips from projects to articles once articles is rebuilt.
- **A Phase-2 batch keeps only the pages it was asked for; a broken summary warns; a colliding summary slug is split (v3.84.0)** — every batch prompt lists ALL planned pages (that block must stay in the byte-stable prefix), and models (Flash-Lite 2.5 in a user's report) answered with every planned page, the summary included, in every batch; `reconcileGeneratedPages` merged the summary copies and `mergeWikiPage` unioned their Key Takeaways (one real summary held 935). `filterBatchReply` (`ingest.js`) now keeps, per batch, only the requested pages; a copy of a page planned for another batch, or of a summary the batch was not asked for, is set aside as a RESERVE and used only where the owning batch returned nothing or a stub (so the filter never turns "written" into "missing"); a page planned by no batch is kept unchanged. Set-aside copies produce NO user-visible warning (stderr only): the warn-on-drop rule is about losing what the model produced, and the page is written by the batch asked for it. The batch suffix (after the cache breakpoint) states the exact page count; the prefix is byte-identical. Also: no empty trunk stub after single-pass or when the parent exists on disk (`validateOutline` opts `singlePass`, `existingFiles`); `summaryShapeWarning` warns (→ For review) when the saved summary lacks a title, a `source:` or Key Takeaways bullets; `resolveSummaryPath` gives a DIFFERENT source with the same slug `<slug>-<6 hex of sha256(filename)>` and a "keeping both" warning, on positive evidence only (manifest record for another filename, or a filename-with-extension `source:` mapping to the same slug) — re-ingesting the same file still merges. Known: a planned page no batch returns still vanishes silently; compile-created summaries and title-valued `source:` are not collision evidence.
- **Batch ingest queue invariants (v3.3.0+)** — the queue directory resolves through `getIngestQueueDir()` in `paths.js` and **must never live inside `getDomainsDir()`** (that is Personal Sync's git work-tree; staged sources would be committed and pushed). Execution is **strictly sequential and process-wide**: the worker/create claims are taken **synchronously**, with no `await` between check and set, and a second independent in-flight counter asserts "at most one `ingestFile` ever" around the call itself — do not "fix" a concurrency report by adding another check after an `await`, that narrows the window rather than closing it. **Duplicates are decided once, at create time, and the worker performs no duplicate check** — `ingestFile` writes `raw/<name>` first, so a runtime check would mark a crash-resumed item `skipped` and silently drop it. A **transient** provider error (structured `err.curatorTransient` tag from `llm.js`, never a bare `/\b429\b/` — that also matches ingest's own `"yielded only 429 characters"`) pauses the whole batch; anything else fails one item; and a **consecutive-failure circuit breaker** bounds the harm regardless of classification. A recovered job comes back **`paused`, never running** — nothing may auto-start spend. `toWire()` is an explicit **allow-list** with length caps and path scrubbing; never reintroduce a `...rest` spread. A `budgetUsd` that cannot be priced is **refused (400)**, never silently accepted — and the cap guarantees spend is *tracked and bounded*, not that it is never exceeded. The estimate quotes a multiple **computed for the batch in front of it**; the fresh-vs-mature ratio is size-dependent (**39.4× at 2 KB → 2.1× at 80 KB**, with a step at ~15,000 chars where a source crosses to multi-phase) so **never hard-code a single multiplier** — a test asserts the multiple must move with document size.
- **An announced product is a primary subject, and writePage's redirects are warnings (v3.81.0, 2026-09-30)** — a user's Haiku ingest of an article announcing their own tool wrote feature concepts but no `entities/<tool>.md`. Cause: the app's prompt required an ORIGINATOR entity (people, companies) and listed tools only among "substantive" entities, and the generic template's system prompt said "person, item, or organization". Fix: `ANNOUNCED_PRODUCT_RULE` in the outline and single-pass prompts only — NOT the Phase 2 batch prompt, which writes exactly the pages the outline planned (a coverage rule there would ask every batch for the page, and the prefix must stay byte-identical); `test-ingest-coverage-v381.js` pins both prompts as v3.80.0 plus exactly that line, and the batch prompt as byte-identical to v3.80.0. Its `(e.g. entities/<product-name>.md — never concepts/)` clause is measured load-bearing for Gemini Flash-Lite (3/6 without, 6/6 with) — do not "tidy" it away. The templates now name tools/products; existing domains' `CLAUDE.md` are the user's and are never rewritten. Separately, `writePage`'s Pass A/B and step 3b redirects were silent (A/B) or stderr-only (3b), against the warnings contract above; they now go through `opts.onWarn` with "redirected to canonical" wording (the result panel's Auto-fixed bucket) and aggregate at 3 (`variant-redirect`, `cross-folder`). App compile now passes `onWarn` too and aggregates its warnings; the MCP's `compile_to_wiki` still does not (its caller sees the canonical paths in `pagesWritten`). NB: 3b is first-write-wins, so a product previously filed as `concepts/x.md` STAYS a concept on re-ingest — the warning now says so, and the user moves the file by hand.

## Chat and compile

- **Conversations gitignored from app repo but synced via knowledge repo** — personal to each user's machine, not committed to source control.
- **Conversation IDs are UUIDs and validated at the route boundary (v2.5.0+)** — `src/routes/chat.js` and `src/routes/compile.js` reject any `conversationId` that doesn't match `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i` before reaching the filesystem layer. Defense in depth — `readConversation` would otherwise build `path.join(conversationsPath, '<id>.json')` from arbitrary client input.
- **Compile has a fallback ladder like ingest (v3.0.1-beta.27+)** — `compileConversation` ([src/brain/compile.js](../../src/brain/compile.js)) tries `full → concise → summary-only`, escalating ONLY on `isOutputTokenLimit(err)` (exported from ingest.js) or a JSON parse failure; ANY other LLM error (503/429/auth/network) surfaces immediately (never masked, no wasted retries). `buildCompilePrompt` takes a `mode` param (`full` is byte-identical to the beta.25 prompt). On total overflow it returns a **compile-specific** error ("conversation too large… compile a shorter thread or split by topic"), NOT ingest's "split the PDF by chapter". Degraded outcomes surface via a `warnings[]` on the result (shown as a `.compile-note` in the result panel). `compileConversation(domain, id, onProgress, opts)` accepts `opts.generateText` — a **test-only** seam to inject a fake LLM (used by `test-beta27-compile-fallback.js`); defaults to the real `generateText`. The summary-only page flows through the unchanged `writePage → syncSummaryEntities → mergeIntoIndex` pipeline.
- **Chat/query truncation is graceful; the MAX_TOKENS message is context-neutral (v3.0.7+)** — the output-token-limit guard in `callProvider` ([llm.js](../../src/brain/llm.js)) is a SHARED chokepoint for every LLM call, so its error must NOT carry feature-specific advice. All MAX_TOKENS handling routes through the exported `handleOutputTokenLimit(providerName, maxTokens, responseFormat, partialText)`: **JSON mode throws** (message must keep the literal phrase "output token limit" so `isOutputTokenLimit` — which ingest/compile fallback ladders key on — keeps matching; no ingest vocabulary like "split the source"/"Phase 2 batch size"), **text mode returns the partial answer + a truncation note** (never throw — a cut-off chat/query answer is still useful). Chat + query request 8192 output tokens (not 4096). Callers wanting feature-specific guidance (ingest, compile) add it at their own level, never in the shared guard.
- **Chat intent routing classifies the ASK, has three intents, and list/count COMMANDS beat decision words (v3.0.8+)** — `detectQueryIntent` in [chat.js](../../src/brain/chat.js) first calls `extractAsk(message)` to isolate the user's actual ask (interrogative sentences → else command-opener sentences → else the whole text) so list-like or decision-like words buried in PASTED CONTENT (a topic idea containing "everything", a pasted "List: A, B, C" line) can't hijack the routing. It then returns `decision | enumerate | synthesis` via an ORDERED router over that ask: (1) a NARROW analytical flag (disagreement words + whole-word `differ` only — never bare "most/least", which appear in benign list phrasing), (2) strong list/count command anchors (`list`/`how many`/`count`/`what|which <plural-noun>`/`all|every <noun>`) anchored to a clause boundary `(?:^|[.?!]\s+|\n)\s*` so they win over incidental decision words and work after a preamble, (3) decision cues, (4) weak list phrases. Order matters — do not move decision above the strong anchors (reopens the "content word hijacks intent" bug), and keep `extractAsk`'s questions-first precedence (a real trailing question must win over a pasted command line). The bare word "everything" must NOT be an enumerate trigger. A superlative/disagreement question shaped like a list request diverts to synthesis. Known accepted trade-off: a decision question that opens with a plural-noun enumerate anchor ("which papers should I read first?") routes to enumerate (a capped, deduped list — a reasonable answer, not a dump). All three `buildPrompt` blocks forbid reproducing the catalogue; `stripCatalogueEcho` is a last-resort net (strips runs of 5+ bare `folder/slug.md` paths separated only by spaces/tabs — never commas/newlines, so legit lists/code/multi-path citations survive; no global whitespace collapse). Tier 2 (a Concise/Balanced/Comprehensive response-style selector) is planned as a later release.
- **Chat response style is orthogonal to intent (v3.0.9+)** — `RESPONSE_STYLES` in [chat.js](../../src/brain/chat.js) (`concise`/`balanced`/`comprehensive`) controls answer DETAIL/LENGTH; `detectQueryIntent` controls answer SHAPE. The style directive is appended AFTER the intent block and MUST NOT relax the anti-catalogue-dump guardrails (comprehensive still forbids reproducing the catalogue; `stripCatalogueEcho` + the enumerate ~40-item cap still apply). `normalizeResponseStyle` MUST use an own-property check (`Object.hasOwn`) — a truthiness guard lets inherited keys (`__proto__`/`constructor`) through to an undefined cap/directive. `balanced` has an empty directive so the 5-arg `buildPrompt` stays byte-identical to the legacy 4-arg call. Every cap stays within both providers' output limits and chat is text mode (graceful truncation), so a larger cap never hard-fails.
- **Chat answers render Markdown via an XSS-safe renderer (v3.0.10+)** — `src/public/markdown.js` (the old shell's file, deleted whole in v3.41.0 — the invariant lives on in `src/public/next/shared/markdown.js`) (`window.renderChatMarkdown`, loaded as a classic script before the `app.js` module; called from `appendMessage` for ASSISTANT bubbles only) turns Markdown into styled HTML. Under the answer, `sourcesHtml(sources)` renders ONE `Sources · N pages` block, one `.page-chip` per page in **page-type colours** (entity/concept/summary/other — the same mapping the reader's backlink chips now share via `shared/page-chip.css`, not the domain's identity colour: every source in one answer is already one domain, so an identity colour there would be one colour on every chip). **The raw path never appears on the answer face** — only in the reader header once opened, and in a chip's visually-hidden accessible name. The hook's number must be a positive integer under 100000 or the marker renders inert (`.chat-cite-unresolved`); a capture containing renderer markup (e.g. a nested `[[wikilink]]`) is never handed to the hook. `test-next-markdown.js` and the new `test-next-answer.js` mutation-prove the escape-first invariant on every new pass.
- **Conversation facts (`updatedAt`, `project`, `priced`) are stored going forward only, and never guessed for a file that predates them (v3.72.0, P1)** — `updatedAt` is written to the conversation file on every **completed** turn (a failed turn leaves the file byte-identical); each new assistant message gets `project` (the pinned project's name, or `null` for "no project this turn") and, when a true figure exists to record, `priced` (the served model's rates and cost, fixed at answer time — never recomputed later against a changed catalogue). A file written before v3.72.0 has none of these keys, and **nothing back-fills them**: the list falls back to `createdAt` for sorting/ageing (rendered as "started … ago", never presented as last use) and shows no project mark. This is the same shape the memory layer's "state SUPERSEDES, never inferred" rule takes elsewhere in this codebase — a missing fact is shown as missing, not reconstructed.
- **Chat conversations are intentionally synced (not a bug)** — `domains/.gitignore` is generated from `DOMAINS_GITIGNORE_RULES` in [src/brain/sync.js](../../src/brain/sync.js) (read the array, don't trust a count in prose — it has grown four times). It currently excludes machine-local and junk paths only: `*/raw/`, `*/.mcp-write-log.jsonl`, `*/.write-lock` (v3.0.15), `.DS_Store` (v3.0.16, deliberately un-prefixed so it matches at any depth), `.ingest-queue/` (v3.3.0, purely defensive), and `**/.obsidian/workspace.json`, `*.base`, `Untitled.md`, `Untitled 1.md` (v3.5.1 — the `**/` on the workspace rule is load-bearing per `gitignore(5)`). `conversations/*.json` is on none of those lists, so it IS tracked by the knowledge repo and travels with the wiki (documented in [sync.md](../../docs/sync.md): "so you can continue threads on any machine"). Consequence: sending one chat message adds exactly one pending change, so the Sync badge legitimately ticks to 1 after a chat with no ingest or compile. Community-reported as suspicious in v3.0.14 and deliberately left as-is. (CLAUDE.md's directory tree labels `conversations/` "gitignored" — that is true of the APP repo only.)
- **Chat is told what it cannot see (v3.81.0, 2026-09-30)** — chat's system prompt is the domain `CLAUDE.md`, whose "Instructions for the AI" describe ingest; asked why an ingest had not created a page, a model holding only that text blamed "an oversight in the instruction execution". `WIKI_ONLY_CLAUSE` in [chat.js](../../src/brain/chat.js) is appended to all three intent blocks unconditionally (unlike `PROJECT_CONFLICT_CLAUSE`, which is project-only): chat sees the wiki's pages and schema, not how any ingest ran nor the app's ingest prompt, so it must say it cannot tell and point to that ingest's warnings in `log.md` and to Wiki health. This deliberately changed the wiki-only prompt for the first time since v3.63.0: `test-chat-project-context.js` §1b KEEPS the recorded v3.63.0 digests and asserts the prompt equals them once that one line is removed, rather than re-recording nine new digests.

## Sync and Shared Brain

- **Shared Brain hardening invariants (v3.0.2+)** — synthesis treats stored contribution payloads as a TRUST BOUNDARY (filter non-string facts; per-page try/catch — one bad payload must degrade, never abort); Shared Brain push/pull/synthesize/revoke MUST register with the write-registry (pull also takes the mirror's `.write-lock`); the `shared-*` domain namespace is reserved for read-only mirrors (refused as contributing domains, refused by all in-app write surfaces via `isDomainReadonly`); transient LLM errors (503/429/network, `isTransientLlmError` in sharedbrain.js) never count toward the permanent-skip strike counter; the Host-header guard in server.js applies to ALL requests (DNS-rebinding defense) — keep loopback forms in `ALLOWED_HOSTS` if the bind address ever changes. The Shared Brain enable toggle lives on the Shared Brain view's own off-state in the `/next` shell (it was Settings → "Shared Brain (beta)" in the old shell, deleted in v3.41.0); the Sync view hosts only the operational section. v3.0.3 additions: synthesis consumes submissions ONLY after all their pages write successfully (watermark + processed_ids in state.last-synthesis — never compare wall clocks across machines); all fellow-supplied strings pass sanitizeFellowText/isSafeLinkSlug before composition and identity comes from the storage path; mirror pulls use writePage's `{replace:true}` + prune (never union-merge into a mirror); GitHub tree truncation must THROW (never silently miss files — Article 17 depends on it); an active `state/revocation-in-progress` marker blocks ordinary synthesis and only a fully-successful revoke clears it.
- **Shared Brain UI/UX invariants (v3.0.4+)** — the frontend Shared Brain card layer must go through the per-connection in-flight registry (`state.cards[id]` plus a `data-conn-id` DOM lookup in `src/public/next/views/shared.js`; it was `_sbInFlight`/`_sbLastResult` in the app.js retired in v3.41.0): status/busy writes resolve the CURRENT card in the DOM (never a captured node), one operation per connection, Disconnect blocked mid-op, final summaries restored on re-render. Pinned by `test-next-sharedbrain-ui-parity.js`, which executes the /next functions rather than scanning source. `read_only: true` connections are Pull-only end-to-end (wizard → card → push/synthesize 400s → `pending_pages` 0) — keep all four layers in sync when touching any of them. `GET /api/sharedbrain/list` must stay cheap (mtime scans only — never LLM/network): the old shell's navbar badge polled it, and although the `/next` badge no longer does, the endpoint is still called on every Shared Brain view entry. Adapter operational warnings go through the `onWarn` channel (throwing callbacks must never break the operation). Wizard panel side effects (link population) belong in `sbWizardGoToStep` (on ENTRY), not in the buttons that leave a panel. **Two of its exports are now load-bearing by NAME (v3.64.0):** `mountSharedSection`/`unmountSharedSection`/`sharedSectionBusy`/`sharedLensFor` — no function in `views/shared.js` may be renamed or moved, because four suites brace-match it and three of them execute what they lift; the same rule holds for `views/ingest.js`'s three exports, `mountIngestSection`/`unmountIngestSection`/`ingestSectionBusy`.
- **Shared Brain admin-credential invariants (v3.0.5+)** — the `sbat_…` admin token is shown ONCE (wizard step 2 or the rotate response) and never again: listings mask it, `patchSharedBrain` refuses it, and only `saveSharedBrain`/the rotate endpoint may write it. The revoke UI must keep the API contract intact (client expands the typed `REVOKE-<short-id>` to the full-UUID literal — never prefill the confirmation). Member identity in `listMembers`/the revoke picker is storage-path-derived, NEVER the payload's `fellow_id` (same rule as synthesis). The card's shown-once token display deliberately skips the post-op list refresh — don't "fix" that by adding one. `data_handling_terms` is persisted on connections so invite re-display reproduces the original deterministic token; treat its absence (pre-v3.0.5) as contributor_retains WITH a user-visible caution.
- **Shared Brain adapter-consistency invariants (v3.0.6+)** — GitHub's contents/tree APIs are only EVENTUALLY consistent (~1-2s): never read-after-write against them on a correctness path. The revoke rebuild takes its baseline via `runLocalSynthesis(…, {stateOverride})`, NOT by re-reading the meta it just wrote; the adapter's SHA-retry default must stay ≥3 with backoff (a single immediate retry loses the create-race — guarded in test-sharedbrain-github-offline). Live tests that read back a fresh commit must poll briefly. Concurrent same-file writes are last-writer-wins by design but must never throw or corrupt (verified live in github-live §6b).
- **`push()`, `pull()` and `setup()` must all guard their commit (v3.0.15+)** — any `git commit` that can be reached with a clean index must be wrapped in `if (!err.message.includes('nothing to commit')) throw err`. `friendlyError` maps that message to `null`, so an unguarded throw surfaces as an **empty** error the user cannot act on or recover from. `untrackStaleWriteLocks()` made this reachable in `push()` by staging a deletion that `git add -A` then cancels.
- **A prior version is content or `null` — never `''` (v3.1.1+).** `loadPriorContent`'s pathspec is **work-tree-relative** (`<domain>/wiki/<path>`) because Personal Sync passes `--work-tree=getDomainsDir()`; a `domains/` prefix matches 0 of ~5,200 tracked files and silently disables every delta. Beyond that, `isNew` is a `=== null` identity check while `buildDeltaPrompt` branches on **truthiness**, so an empty-string prior makes the prompt self-contradictory ("IS NEW PAGE: false" + the new-page block) and the model can route real content into `stable_facts`, **which nothing reads** — permanent loss. 0-byte pages are ordinary input (Obsidian creates them on "new note" and the vault root IS `domains/<d>/wiki/`), so `if (!content) return null` is load-bearing, not defensive. Whitespace-only is deliberately NOT caught — it is truthy, so both consumers already agree. Do not over-credit `--literal-pathspecs`: it has been over-claimed twice and now guards no observable output difference.
- **Pages that never reached the collective must never be diffed (v3.1.1+).** A page in `pending_retry`/`permanent_skip` failed its last push, so none of its body was contributed; diffing it against the pre-failure git version drops everything that was never sent. Freeze the membership set off `connection` BEFORE the un-skip loop mutates the working copies. Redundant full contributions are absorbed by exact-string dedup; a gap is unrecoverable — always prefer the redundancy.

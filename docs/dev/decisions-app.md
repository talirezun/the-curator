## Product shape and UI

- **No vector DB / embeddings** — the decision stands, but **not** because the wiki fits in one context window; it stopped fitting long ago (the real `articles` wiki is ~4.4 MB against a 60 KB content budget). What replaced the "just send everything" assumption is **query-driven retrieval in `src/brain/chat.js`**: entity-pivot detection, keyword scoring, and a compact slug catalogue select the pages to load within `CONTENT_BUDGET_CHARS` (60 KB), `CATALOGUE_BUDGET_CHARS` (12 KB) and `MAX_PAGES_LOADED` (50). The reason to stay embedding-free is that the `[[wikilink]]` graph is already a hand-curated relevance signal, and markdown files stay human-readable and Obsidian-native — not that the corpus is small. (A blunt 90 KB `slice()` was the pre-beta.11 behaviour and was a genuine bug: on a mature domain the chat saw only `index.md` and `log.md`.)
- **No React/Vue** — a three-place rail, Chat · Domains · Context, with Sync and Settings in the footer (v3.64.0; was a seven-tab UI Chat · Ingest · Wiki · Health · Domains · Sync · Settings). Ingest and Shared Brain moved onto the domain page as HOSTED_VIEWS — hosted sections, registered and navigable, but with no rail button of their own — and, since v3.64.1, are laid out as five numbered sections under an OVERVIEW card, with their open/closed fold state and the PAGES lens held as one install-wide preference rather than per domain. **Six standing design rules, from v3.64.2 (the fourth added v3.65.0, the fifth and sixth v3.65.1), for every view builder from now on:** (1) **one overview card** (`renderOverview()` in `shared/overview.js`) for the readings *about* a screen, shared by every host rather than each view growing its own — the domain page's OVERVIEW and the Context page's three-layer readings are the same component, one rendered function, not two; (2) **one heading rule** — every numbered section on a page carries a numeral at one fixed x position and a Title-case title (e.g. 1 Ingest, 2 Pages, 3 Projects in this domain, 4 Shared Brain, 5 Wiki health, not ALL CAPS) above its own card, the head a SIBLING of the card or fold and never a wrapper around it; (3) **the step-body rule** — a step or section's body is uniform fold rows, with the explanation only in the ⓘ, never inline, and its one standing exception since v3.16.1: a warning, a cost or an outcome may never sit behind a chevron; (4) **the monitor** (`renderMonitor()` in `shared/monitor.js`, v3.65.0) — every LIVE-STATE reading in the app renders through one recessed, mono-faced component, distinguished from a `.cur-group` and from a fold row's `<summary>` (an incidental reading), with the v3.16.1 exception carried INSIDE it as a `loud` entry — always rendered, never wrapped in a `<details>`; (5) **continuity by identity** (v3.65.1) — one domain, one colour, EVERYWHERE it is named: one palette (the twelve `.cur-sb-dot-N` rules, `shared/sidebar.css`), one mapping (`identityDotClass(i)` in `shared/sidebar.js`, keyed on the install's own domain index — position N is position N on every screen), one glyph (`.cur-sb-dot`, 8px, round, resized or reshaped by no view); a sidebar row, a Chat domain chip, an Ingest destination row, a Knowledge row and the Context breadcrumb all carry it, and no surface may invent a second mapping or a second palette; (6) **the depth bar** (`renderDepthCell()` in `shared/monitor.js`, v3.65.1) — the THIRD visual channel, SIZE/SHARE, beside TIME (the freshness dot) and WHICH DOMAIN (the identity dot, rule 5): a tinted bar behind a figure, right-anchored, its length a NAMED denominator (a budget, or the largest visible row) — never a time, never inside a `<summary>` or a sidebar row, and wherever it turns danger-toned the same fact is also stated in words, unfolded (v3.16.1). **Every sidebar in the app is also one component since v3.65.0** (`shared/sidebar.js`, `renderSidebarHead`/`Group`/`Row`) — Domains, Context and Settings all render through it: a title with no ⓘ, at most two actions stacked under it, an eyebrow group, rows of identity dot · name · figure · freshness mark · clock glyph + age · last-event line; active is the filled row (a `--mat-row-*` alpha overlay), never a left edge — the violet `::before` selection bar Settings and Chat's conversation list each once used on their own is gone from both, with no rule left to bring it back. Still vanilla JS, no build step.
- **JSON mode for ingest, text mode for chat** — ingest requires structured output; chat needs free prose.
- **UI auto-refreshes after mutations** — after ingest, domain stats (page count, conversation count) update automatically; after sync down/both, domain dropdowns and stats also refresh; switching to the Domains or Wiki tab reloads their data. No manual browser reload needed.
- **First-run guidance is a non-blocking, dismissible panel, not a wizard (R7; two doors since v3.61.0)** — the old `/old` shell's **4**-step blocking modal (API keys → create domain → sync setup → connect Claude Desktop, with no Skip on step 1 and no Escape/backdrop-close/X) described in this bullet through v3.60.0 no longer exists: `src/public/app.js` and the rest of the old shell were deleted whole in v3.41.0, and `/` has served `/next` exclusively since. The **current** panel is [`src/public/next/views/onboarding.js`](../../src/public/next/views/onboarding.js), built against a private design handoff's binding decision R7 (its header comment quotes the rejection of a first-run wizard verbatim): no scrim, no `role="dialog"`, no `aria-modal`, no focus trap — a labelled region layered over the real UI, opened once from `app.js`'s `boot()`, survives `navigate()`, and every step **points** at the real surface that owns that job rather than embedding an input or posting anything itself. **Two doors, as of v3.61.0** (`DOORS` / `STEP_SETS` in `onboarding.js`), because the three-step order was actively wrong for half the app's audience: *"Build a second brain"* (id `knowledge`, lands on Domains) walks `api-key → domain → ingest` — reading a lot and wanting a wiki out of it, where nothing works without a model first; *"Give your agents memory"* (id `agent`, lands on Agent memory) walks `domain → project → bridge → api-key`, with the key step's copy corrected to name what actually needs it (*"Needed for ingest and chat. Agent memory and the bridge work without one."*) rather than the old, now-false "nothing else works without a model" claim. Neither door is stored as a persona: `deriveDoor()` re-derives which one applies from on-disk facts every paint (a stored preference would go stale the moment the user does the other thing), and pressing a door writes only `app.js`'s **existing** `curator-next-view` last-view key — no new storage key, no separate preference. The trigger for showing the panel at all is still **CONFIG-ONLY** — `hasApiKey()` reads `hasGeminiKey || hasAnthropicKey` from `GET /api/config/api-keys`, which resolve through `getApiKeys()`'s `.curator-config.json` **only, never `.env`** (the same invariant this file has stated since v3.0.13; a `.env`-only developer still sees the panel, harmlessly, since it is dismissible) — and readiness facts for every step are read the fail-safe direction: a failed fetch answers all-false, which **shows** the panel rather than hiding it.
- **Theme has no `--text-dim` var (v3.0.12 note)** — the CSS custom properties for text are `--text` (#cdd6f4, primary), `--text-2` (#a6adc8, secondary/dim), `--text-muted` (#6c7086, faint), `--text-faint`. `var(--text-dim)` is INVALID and silently falls back to the element's inherited/UA colour (black on a `<button>`). Use `--text-2` for "dim but readable" text. When styling a menu/option built from `<button>`s, set an explicit `color` on the button so children don't inherit the UA default black.
- **The boot guard lives in `index.html`, not `app.js` (v3.0.15+)** — a handler inside `app.js` cannot catch `app.js` failing to evaluate, which is the exact case (~79 top-level `getElementById` consts; one missing element blanks the page for every user via the auto-updater). Only the `window.__curatorBooted` sentinel, set on `app.js`'s last line and checked at `DOMContentLoaded`, is authoritative — do NOT add filename-based resource-error heuristics, because the SPA fallback serves `index.html` with a **200** for any missing path, so a missing script throws a `SyntaxError` rather than a resource error. A missing `markdown.js` is NOT fatal (`app.js` has a designed escaped-text fallback) and must never trigger the panel.
- **CSS custom properties fail silently — `npm test` guards them (v3.0.15+)** — an undefined `var(--x)` makes the declaration invalid at computed-value time (inherited properties fall back to `inherit`, so it often looks *almost* right). [test-css-tokens.js](../../scripts/test-css-tokens.js) fails on any new undefined reference and carries named regression guards for `--font-mono` and `--text-1`. Three fallback-carrying names (`--text-primary`, `--text-secondary`, `--surface-1`) are deliberately baselined — re-pointing them at real tokens would change rendered colours, which belongs with the design-system work. Never add a variable to the baseline to make the suite pass.

## App lifecycle, install and update

- **install.sh auto-provisions** — detects and installs Node.js (via Homebrew or nodejs.org .pkg) and git (via Xcode CLI tools); no longer asks for API key during install (onboarding wizard handles it); auto-opens the app on completion.
- **No Stop button** — removed entirely because AppleScript's `on reopen` handler is broken on modern macOS and caused unrecoverable crashes. Closing the browser tab leaves the server running in the background (uses ~0 CPU). Clicking the Dock icon re-opens the browser if the server is running, or starts the server if it is not. To fully quit: right-click the Dock icon → Quit.
- **No /api/shutdown endpoint** — the server runs until the process is explicitly killed (Dock → Quit, or terminal Ctrl+C). No heartbeat or auto-shutdown.
- **Auto-update via Settings** — compares local `package.json` version with GitHub's `main` branch; runs `git fetch origin main` + `git reset --hard origin/main` + `npm install` + `bash scripts/build-app.sh` (rebuilds the .app); returns `{from, to}` short SHAs; frontend then calls `/api/restart` which spawns a new process and exits the old one. Browser auto-reloads. The hard-reset (instead of `git pull`) means the app directory is always forced to match `main` exactly — `package-lock.json` regenerated by local `npm install` runs no longer blocks the update.
- **Server auto-opens browser** — `exec('open http://localhost:3333')` runs on startup, unless `CURATOR_NO_OPEN=1` is set (used by the restart endpoint to prevent double browser tabs — the frontend reloads itself via polling).
- **Absolute node path in AppleScript** — `build-app.sh` and `install.sh` resolve the full path to `node` (via `which node`) at build time and embed it as `property nodeBin` in the AppleScript. This avoids the "node: No such file or directory" failure caused by AppleScript's `do shell script` running in a bare `/bin/sh` environment without the user's PATH. A `export PATH=...` with common node locations (`/usr/local/bin`, `/opt/homebrew/bin`) is also added as a fallback. If the user upgrades or moves Node.js, `bash scripts/build-app.sh` re-resolves the path.
- **Restart uses `process.execPath`** — the `/api/restart` endpoint uses the absolute path to the currently running Node binary (`process.execPath`) instead of bare `node`, ensuring the restarted server finds the same Node regardless of shell environment.
- **Versioning policy (v3.0.2+, user decision 2026-07-02)** — plain semver `MAJOR.MINOR.PATCH`, **no pre-release suffixes**. The old `3.0.1-beta.N` line shipped 27 consecutive "previews" straight to production via the auto-updater, so the `-beta` tag carried no meaning and confused users; it is retired. Each release bumps PATCH (Shared Brain hardening: Phase 2 → 3.0.3, Phase 3 → 3.0.4); a feature milestone like Shared Brain GA bumps MINOR (→ 3.1.0). Feature-level beta status is expressed in the UI (e.g. the Shared Brain "beta" pill), independent of the app version. New test suites are named by feature (`test-sharedbrain-hardening.js`), not by release codename.

## Models, keys and money

- **API keys UI-first** — `.curator-config.json` (set via Settings tab / onboarding wizard) takes priority over `.env`. The `.env` file remains as a developer fallback.
- **Model-lifecycle policy (v2.4.0; active-provider rules rewritten v3.45.0)** — single chokepoint for all LLM calls is `generateText()` in `src/brain/llm.js`, which dispatches to whichever provider is ACTIVE. **How a provider becomes active (Option B, v3.45.0):** saving a key sets it **only when nothing is active yet**; thereafter the writer is **choosing the build model**, and a key save leaves the lane where it is. Disconnecting the active provider falls to the **cheapest measured connected** provider, and records an explicit `null` when every candidate is refused rather than leaving the field absent for the legacy ladder to re-infer from. `ACTIVE_PROVIDER_DERIVED = false` in [src/brain/config.js](../../src/brain/config.js) restores the old last-saved-wins behaviour. Default models are pinned in `DEFAULTS`; `FALLBACK_CHAINS` provides an ordered next-best list per provider. On model-not-found errors (and ONLY those — 429/503 still retry) the chain is walked in order; the successful model is recorded in a module-level `_activeFallback` and surfaced to the UI via `getFallbackStatus()`. When a provider retires a model: bump the `DEFAULTS` constant, optionally add the old primary to `FALLBACK_CHAINS`, push a release. Users on older versions keep working via the chain until they Check for Updates. Full user/developer guide: `docs/model-lifecycle.md`.
- **The Gemini fallback chain must escalate FORWARD in time, and every rung must be priced (v3.0.15+)** — `FALLBACK_CHAINS.gemini` exists to keep users working when the pinned default is retired, so it must list *newer* models, never older ones. The pre-v3.0.15 chain pointed at `gemini-1.5-flash*`, both of which were already **404** — the safety net had one working rung. When adding a rung: probe it live with the app's real call shape (JSON mode + `maxOutputTokens: 65536`), add its price to `MODEL_PRICES_USD_PER_MTOK` (an offline invariant in `test-chat-model.js` fails `npm test` otherwise), and never describe a rung as "same cost tier" without checking — a family-name heuristic is structurally wrong because the family word is stable across generations while the price is not (`2.5-flash-lite` → `3.1-flash-lite` is 2.5× in / 3.75× out; `haiku-4-5` → `3-5-haiku` is genuinely *cheaper*). `DEFAULTS.gemini` stays on the cheapest working model; the chain is insurance, not a migration.
- **`getProviderInfo` FALLS THROUGH — never infer the provider from the label (v3.1.1+).** With no key for the requested provider it silently returns whichever provider still has one. Any test that redirects user-data paths also redirects `.curator-config.json` (where the Gemini key lives; it is not in `.env`), so a "per-provider" suite can run one model twice and pass. Seed the isolated config AND assert the resolved provider. Byte-identical output from two different models is the tell.

## Security, credentials and user-data paths

- **Server binds to 127.0.0.1 only (v3.0.1-beta.20+)** — `app.listen(PORT, '127.0.0.1', ...)`. The Curator is a single-user localhost app; binding to all interfaces (the pre-beta.20 default) exposed unauthenticated endpoints to the LAN. A cross-origin guard middleware additionally rejects mutating requests (POST/PUT/DELETE/PATCH) carrying a non-loopback `Origin` header (CSRF / DNS-rebinding defense); no-Origin requests (curl, scripts, the revoke flow) and all GETs pass through. The 50mb `express.json` body limit remains (Health batch plans) — that's safe precisely because the server is loopback-only.
- **Credential files are 0600 + atomic (v3.0.1-beta.20+)** — `.curator-config.json`, `.sync-config.json`, `.sharedbrain-config.json` all write through `writeFileAtomic`/`writeFileAtomicSync` with the new `{mode: 0o600}` options form (explicit `chmod` of the tempfile before the atomic rename, so umask can't loosen it). A startup sweep in `src/server.js` also hardens those plus `.env` and `.knowledge-git/config` (PAT-bearing) for existing installs. When adding any new file that holds a secret, write it with `mode: 0o600` and add it to the startup sweep list.
- **All user-data paths resolve through `src/brain/paths.js`; bundle detection is POSITIVE and fail-safe (v3.1.0+)** — an installed `.app` is read-only, so writing inside it breaks the code signature. `isBundleInstall()` requires an EXPLICIT signal (marker file or `<X>.app/Contents/` path shape); **everything else is repo mode — an unrecognised layout must ⇒ repo ⇒ data stays put.** Never invert this to "infer repo from markers, default to bundle": wrongly deciding "bundle" is catastrophic AND silent (empty wiki, data invisible), while wrongly deciding "repo" fails loudly on first write with nothing lost. Two earlier attempts were both wrong — `existsSync('.git')` alone (a ZIP download relocated everything) and data markers including `domains` (which `domains/.gitkeep` puts in EVERY shipped tree, making bundle mode unreachable). Any new user-data path MUST route through `paths.js` — there is exactly one root derivation in `src/`+`mcp/` and a source guard enforces per-call resolution (no top-level `const X = <getter>()`, which made an override silently import-order dependent). `scripts/build-app.sh` must NOT write the bundle marker while the `.app` remains an AppleScript wrapper around the checkout.

## Tests and CI

- **Test suite is run via `npm test` (v3.0.1-beta.21+)** — one aggregator ([scripts/run-tests.js](../../scripts/run-tests.js)) runs all battle-test suites. `npm test` = offline only (free, no network, credentials stripped from children); `npm run test:live` = + live API suites. When adding a new test script, add it to the OFFLINE or LIVE array in the runner. Tests that need to redirect the domains dir to a tempdir MUST use `__setDomainsDirOverride()` from `config.js` (checked before config) — NOT `process.env.DOMAINS_PATH`, which loses to a configured `domainsPath` and silently no-ops on real installs.
- **CI runs on GitHub Actions** ([.github/workflows/test.yml](../../.github/workflows/test.yml)) — two jobs. `offline`: every push + every PR (incl. forks); `npm ci` + `npm test`; free, no secrets. `live`: gated to push-`main` + manual `workflow_dispatch` only, `needs: offline`, uses `GEMINI_API_KEY`/`ANTHROPIC_API_KEY` repo Secrets (optional `GITHUB_TEST_REPO`/`GITHUB_TEST_PAT`). The live job never runs on PRs, and GitHub also withholds secrets from fork PRs — so fork contributors can't reach the keys. CI is dev infrastructure only: no app code, schema, or version change. Setup/secret instructions live in [CONTRIBUTING.md](../../CONTRIBUTING.md).
- **Live test domains-dir isolation (v3.0.1-beta.23 follow-up).** The live suites had the SAME domains-dir isolation bug the offline suites had pre-beta.21 — they isolated via `process.env.DOMAINS_PATH` (defeated by a configured `domainsPath`) or wrote throwaway domains straight into `getDomainsDir()`, so `npm run test:live` polluted the real `domains/` folder on a configured dev machine (verified: it created `domains/zztest-beta15-anthropic/`). **Fix:** new `CURATOR_TEST_DOMAINS_DIR` env seam in `getDomainsDir()` ([config.js](../../src/brain/config.js)) — checked BEFORE config (unlike `DOMAINS_PATH`), so it works on a configured machine AND across a spawned child process (the routes test's server). Test-only; unset in production. All live suites that create domains now set it to a tempdir. **Manifest split** in [run-tests.js](../../scripts/run-tests.js): `LIVE_CI` (self-contained, deterministic — beta8-live-llm, beta14, beta15/16/17-production) runs on CI + locally; `LIVE_LOCAL` (beta13-chat-live = real `articles` data + LLM-quality asserts; ingest-real-llm = a SPECIFIC personal article on a hardcoded local path; ingest-deep = quality thresholds; sharedbrain-github-live = needs `GITHUB_TEST_*`; sharedbrain-routes = spawns a server) runs only locally and is auto-excluded when `CI=true`. Per-suite timeout is tiered: offline 2 min, live 10 min (dual-provider ingests legitimately take minutes). **A first CI live run (run #2) surfaced two suites reading files absent on a clean checkout:** `beta15-production` read `domains/projects/raw/ingestion-pipeline.md` purely as a large multi-phase source → repointed to the committed `docs/ingestion-pipeline.md` (~35k chars; assertions are behaviour-based, so content-agnostic) → stays in CI; `ingest-real-llm` is tied to a specific personal article (asserts author "Dr. Alice Smith") via a hardcoded `/Users/...` path → moved to `LIVE_LOCAL`. The Anthropic key was NOT the problem — `test-beta14-anthropic-fix` passed on CI, confirming the secret works. Verified: a `CI=true` live run isolates cleanly (zero domains/ pollution).
- **Live-CI gate tolerates transient provider errors (v3.0.1-beta.26+)** — the live-API job hits real Gemini/Anthropic, so a provider 503 / dropped stream / rate-limit / network blip would otherwise red the build for reasons that are not code defects. [scripts/run-tests.js](../../scripts/run-tests.js) retries any failed LIVE suite **once**; if it still fails showing **only** transient markers (`scripts/ci-flake.js` `hasTransientMarker`), it's reported **inconclusive** (⚠ flake) and does NOT fail the build; a second failure with no transient marker is a genuine FAIL. Offline suites are deterministic and never retried. The `RUN_TESTS_LIVE_ONLY` env is a **test-only** seam (drives the runner against `scripts/test-fixtures/` fakes in `test-runner-integration.js`) — unset in normal runs and CI. When adding a new transient failure string the providers emit, add it to `TRANSIENT_MARKERS` in `ci-flake.js`. Trade-off: a real failure coinciding with a transient error in the same run is reported inconclusive — accepted because the offline suite + local `test:live` still catch real regressions.
- **System Check is read-only w.r.t. user data (v3.0.1-beta.23+)** — `src/brain/diagnostics.js` powers Settings → System Check (UI label "System Check"; internal element IDs/classes keep the `diag-*` prefix). `runQuickDiagnostics()` is free + local (no network, no API); its only write is a self-deleting temp-file probe to test that the domains folder is writable — it never reads or writes wiki content. `runLiveApiCheck()` is opt-in, makes ONE tiny LLM call (~$0.0001), is gated behind a frontend cost-confirm + the POST cross-origin guard, and never throws. Both dispatch through `getProviderInfo()`/`generateText()`, so the feature is provider-agnostic (verified on Gemini + Anthropic).
- **If a test spawns a server, isolate with `CURATOR_TEST_USER_DATA_DIR`, not `CURATOR_TEST_DOMAINS_DIR` (v3.1.0+)** — the latter isolates ONLY `domains/`, so a test server holds the developer's real `.sync-config.json` and GitHub PAT, and one stray Sync click pushes to their real repo. The new env is read before repo/bundle detection and re-read per call, so it crosses process boundaries; it isolates all four credential locations unconditionally, and `domains/` too UNLESS `DOMAINS_PATH`/`--domains-path` is set. (`scripts/test-sharedbrain-routes.js` still needs migrating.)
- **Give a clever test an independent dumb cross-check (v3.1.0+)** — `test-frontend-null-safety.js` was silently blind TWICE while reporting every assertion green: its lexer desynced on a nested template literal and on a regex containing backticks (seeing 78 of 90 declarations), and the rewrite then shipped a dead regex-vs-division heuristic that reopened the class. A parity tripwire could not catch it (two desyncs cancel). What works is a second, deliberately-dumb measurement compared for exact SET equality — it fires even on shapes the sophisticated path still misses. Same lesson as v3.0.15's CSS-token baseline and v3.0.17's source-regex assertion: a passing test that measures the wrong thing is worse than no test.
- **Assert behaviour, not the presence of a line of source (v3.0.17+)** — `test-ingest-prompt-slimming.js` asserted the CALL SITE of the Phase 1 usage report with a source regex and labelled it "the pages-vs-tokens datapoint sizing needs". The value it reported was ALWAYS wrong on the retry path (a dead `if (outline)` conditional inside `if (!outline)`), and the source assertion gave positive assurance the whole time. A test that proves a line exists proves nothing about what it does. `ingestMultiPhase` now takes a trailing defaulted `llm` param — a TEST-ONLY seam (same pattern and rationale as `compile.js`'s `opts.generateText`, null in production) that drives the real Phase 1 retry ladder and Phase 2 fallback ladder against a fake LLM, offline and free. Building that seam is what surfaced the lenient-`parseJSON` bug below; prefer it over source regexes for anything orchestration-shaped.
- **`npm test` must never touch a real credential file (v3.1.1+).** Suites needing a different domains dir use `__setDomainsDirOverride()` (in-process, domains-only) or `CURATOR_TEST_USER_DATA_DIR` (anything spawning a server) — never by deleting the real config so `DOMAINS_PATH` can win. Fingerprint guards compare **sha256 + size + existence only**: `mtime` makes them fail when the maintainer's live app rewrites config during an ordinary Settings action, producing a false "isolation is broken" — the misattribution shape that cost two investigations in v3.0.16.

## Known benign GitHub behaviours

- **"Sorry, we had to truncate this directory to 1000 files"** on GitHub's web UI when browsing `domains/articles/wiki/concepts/` (or similarly busy folders) is a **GitHub rendering limit, not a sync issue**. Git itself handles millions of files per directory; the truncation only affects the file-listing view on `github.com`. Clone the repo locally, or use `git log` / `git ls-files`, and you see everything. Sync push/pull transfers all files correctly regardless of this UI limit.
